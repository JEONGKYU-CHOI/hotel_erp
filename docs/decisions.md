## D-001. 프론트엔드 — 하이브리드 (부킹엔진 React / 백오피스 Thymeleaf)

**결정일** 2026-07-29
**부분 폐기** 인증 부분은 [D-008](#d-008-부킹엔진-인증--jwt-d-001-부분-supersede)이 대체한다.
아래 표의 "인증 = 없음" 항목은 더 이상 유효하지 않다. 프론트 기술 선택은 그대로 유효하다.

**결정**

| 영역 | 기술 | 인증 |
|---|---|---|
| 부킹엔진 (고객) `/` | React + Vite | ~~없음 (비회원 예약)~~ → **JWT (D-008)** |
| 백오피스 `/admin/**` | Thymeleaf + Bootstrap | 세션 쿠키 (Spring Security) |
| API `/api/**` | REST (부킹엔진 전용) | ~~없음~~ → **JWT (D-008)** |

**이유**

1. **포지션이 진짜 풀스택(반반)** — 프론트 코드도 면접 검토 대상이므로 React 산출물이 필요하다.
2. **프론트 역량 증명에 화면 개수는 기여하지 않는다** — 잘 만든 5화면 > 대충 만든 15화면.
   부킹엔진은 보여줄 것이 있다(날짜 범위 선택, 잔여 재고 표시, 결제 플로우, 예약 상태 전이).
   백오피스 CRUD 15개를 React로 만드는 것은 같은 폼의 반복 노동이며 역량 증명에 기여하지 않는다.
3. **JWT 인증 비용(약 8h)을 회피한다** — 고객용 부킹엔진은 비회원 예약(예약번호+전화번호 조회)이라
   인증이 아예 없다. 백오피스는 Thymeleaf라 Spring Security 세션 쿠키 기본값으로 끝난다.
   전면 React였다면 관리자 인증을 위해 JWT 발급/저장/갱신을 직접 설계해야 했다.
4. **CORS가 발생하지 않는다** — 개발 중에는 Vite 프록시, 배포 시에는 React 빌드 결과물을
   스프링 `static/`에 포함해 단일 오리진. 배포 산출물은 JAR 하나로 유지된다.
5. **실무에서 흔한 패턴** — 고객 대면 SPA + 어드민 서버 렌더링. 근거를 설명할 수 있으면
   "일관성 없음"이 아니라 의사결정이다.

**감수하는 대가**

- 스택이 둘이라 프로젝트 구조가 복잡해진다 (`frontend/` 디렉토리 + Gradle-npm 빌드 연동).
- React 라우팅을 위한 SPA fallback 설정이 필요하다 (`/admin/**`, `/api/**`와 경로 충돌 주의).
- 백오피스 프론트 코드는 포트폴리오의 프론트 역량 증거로 쓸 수 없다.

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| 전부 Thymeleaf | 포지션이 풀스택 반반이므로 프론트 산출물이 없으면 절반을 포기하는 셈 |
| 전부 React | 백오피스 15화면 React화에 약 15h. 반복 노동이며 역량 증명 기여도 낮음. 관리자 JWT 인증 비용 추가 |

**기각된 근거 (기록용)**

"등록 → 예약 → 결제를 직접 해보고 싶다"는 목적은 React 선택 근거가 **아니다**.
해당 흐름은 Thymeleaf로 동일하게 구현되며, 특히 결제는 토스페이먼츠 SDK가 어차피 JS이고
핵심(금액 위변조 검증, 멱등성, 승인 API 호출, 재고 복원, 웹훅 중복 처리)은 전부 서버 코드다.
React 선택의 유효한 근거는 **풀스택 포지션에서 프론트가 평가 대상이라는 점** 하나다.

## D-002. ORM — JPA 단독 (락·통계는 native query)

**결정일** 2026-07-29

**결정** Spring Data JPA 단독 사용. MyBatis를 추가하지 않는다.
재고 락 쿼리와 통계 쿼리는 `@Query(nativeQuery = true)`로 SQL을 직접 작성한다.

**이유**

1. MyBatis는 이미 실무 경험이 있어 포트폴리오에서 재증명할 가치가 낮다. 새로 배우는 JPA가 가치다.
2. **혼용하면 도망갈 길이 생긴다** — 재고 락에서 JPA가 막히는 순간 "이건 MyBatis로 짜자"가 되고,
   그러면 JPA 도입 목적이 소멸하며 "왜 둘 다 썼나"에 답할 서사도 없다.
3. 락 쿼리는 native query로 쓰면 `ORDER BY stay_date FOR UPDATE`가 코드에 명시적으로 드러나
   오히려 설명하기 좋다.
4. 서사가 명확해진다 — "MyBatis 실무자가 JPA로 전환하며, 락이 필요한 지점만 SQL을 되찾아온 이유".

**감수하는 대가**

- JPA 학습 곡선을 정면으로 맞는다 (실무 경험 없음). Day 0 스파이크로 완화한다.
- 통계 쿼리를 JPQL로 쓰기 어려워 native query 비중이 늘어난다.

**폐기한 대안** JPA + MyBatis 혼용 — 위 2번 사유.

## D-003. 임시점유(Hold) — DB 상태 + 스케줄러 (Redis 미사용)

**결정일** 2026-07-29

**결정** 별도 Hold 테이블을 두지 않는다. 예약 자체를 `status = HOLD`로 생성하고
`hold_expires_at` 컬럼으로 만료를 관리한다. 스케줄러가 만료분을 `EXPIRED`로 전환하며
`room_inventory.held_qty`를 차감한다.

**이유**

1. **Redis는 재고 진실의 출처를 둘로 만든다** — Redis와 DB가 어긋나면 곧 오버부킹이다.
   동시성 정합성이 주제인 프로젝트에서 정합성 위험을 자진 도입할 이유가 없다.
2. Redis TTL을 써도 **DB 재고 복원은 별도 코드가 필요하다** — 만료 이벤트를 받아 DB를 고쳐야 하므로
   인프라만 늘고 문제는 그대로다.
3. 예약을 HOLD 상태로 만들면 **예약번호를 미리 발급해 PG에 넘길 수 있고**, 결제 성공 시
   상태만 전이하면 된다 (행 이동 불필요).
4. 만료된 HOLD가 `EXPIRED`로 남아 이탈 예약 통계가 부수적으로 확보된다.
5. 면접 가치 — "Redis 썼습니다"보다 "Redis를 검토하고 안 쓴 이유"가 강하다.

**감수하는 대가**

- 스케줄러 주기만큼 재고 반환이 지연된다.
  → **완화**: 가용 재고 조회 시 `hold_expires_at < NOW()` 인 건을 만료로 취급하면
    사용자에게는 지연이 보이지 않는다. 스케줄러는 정리(cleanup)만 담당한다.
- `reservation` 테이블에 EXPIRED 행이 누적된다 (감사 가치가 있어 삭제하지 않음).

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| Redis TTL | 재고 진실의 출처 이원화. DB 복원 코드는 어차피 필요 |
| 별도 `hold` 테이블 | `reservation.status = HOLD`로 충분. 테이블만 늘어남 |

## D-004. 야간마감 배치 — `@Scheduled` + 직접 구현 (Spring Batch 미사용)

**결정일** 2026-07-29

**결정** Spring Batch를 쓰지 않고 `@Scheduled` + 마감 이력 테이블 + 유니크 제약으로
멱등성을 직접 구현한다.

**이유**

1. **Spring Batch를 쓰면 재실행 방지를 프레임워크가 해준다** — 그러면 "제가 설계했습니다"라고
   말할 수 없다. 이 프로젝트의 핵심 기술 과제 ③이 멱등성 설계인데 그것을 위임하면 가치가 사라진다.
2. 러닝커브가 크고(Job/Step/Reader/Writer/Chunk), 메타 테이블 6개가 DB에 생긴다.
3. 마감은 하루 1회 실행이라 청크 처리·재시작 같은 Batch의 강점이 필요 없다.

**감수하는 대가**

- 재시도·스킵·재시작 같은 배치 인프라를 직접 만들어야 한다 (범위를 좁혀 대응).
- "왜 Spring Batch를 안 썼나" 질문에 답변을 준비해야 한다.

**폐기한 대안** Spring Batch — 위 1번 사유.

## D-005. 스키마 관리 — Flyway + `ddl-auto: validate`

**결정일** 2026-07-29

**결정** Flyway로 마이그레이션 SQL을 직접 작성하고, Hibernate는 `ddl-auto: validate`로
검증만 시킨다. `update`를 쓰지 않는다.

**이유**

1. **핵심 설계가 Hibernate 자동생성으로는 나오지 않는다** —
   데드락 방지의 핵심인 `INDEX (room_type_id, stay_date)`와
   최후 방어선인 `CHECK (sold_qty + held_qty <= total_qty)`는 SQL로 직접 써야 한다.
2. **JPA 무경험 상태에서는 `validate`가 안전장치다** — 엔티티 매핑이 틀렸을 때
   테이블을 조용히 바꿔버리는 대신 애플리케이션 시동이 실패한다.
3. 스키마 변경 이력이 파일로 남아 "스키마 변경을 어떻게 관리했나"에 답할 수 있다.

**감수하는 대가** 엔티티를 고칠 때마다 마이그레이션 SQL을 함께 써야 한다 (의도된 마찰).

**폐기한 대안** `ddl-auto: update` — 위 1·2번 사유.

## D-006. 테스트 — 핵심 3과제 통합테스트 + Testcontainers

**결정일** 2026-07-29

**결정** 전 도메인 테스트를 포기하고 핵심 3과제에 통합테스트를 집중한다.
DB는 H2가 아닌 **Testcontainers로 실제 MySQL**을 띄운다.

필수 테스트 3종:
1. 동시 예약 시 오버부킹 0건 (JUnit + `CountDownLatch`)
2. Hold 만료 시 재고 복원
3. 야간마감 2회 실행 시 중복 게시 없음

**이유**

1. **H2로는 `FOR UPDATE`의 행 락이 재현되지 않는다** — 갭 락·넥스트키 락 동작이 다르고
   데드락도 발생하지 않는다. "오버부킹 0건"이 이 프로젝트의 핵심 주장인데
   그 증명을 다른 DB에서 하면 주장 자체가 무너진다.
2. JMeter보다 JUnit 동시성 테스트를 우선한다 —
   세팅 30분 vs 2~3h, **테스트 코드가 리포에 남고** 면접관이 직접 돌려볼 수 있다.
   JMeter는 시간이 남으면 처리량 수치용으로 추가한다.

**감수하는 대가** 테스트 실행 시 Docker가 떠 있어야 하고 실행 시간이 길어진다.

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| H2 인메모리 DB | 행 락 재현 불가 → 동시성 테스트가 무의미 |
| JMeter 우선 | 세팅 비용이 크고 결과물이 리포에 남지 않음 |

## D-008. 부킹엔진 인증 — JWT (D-001 부분 supersede)

**결정일** 2026-07-29

**결정** 부킹엔진(`/` React)과 `/api/**`의 인증을 **JWT**로 한다.
D-001의 "부킹엔진 인증 없음"을 대체한다. 백오피스 세션 쿠키 방식은 그대로 둔다.

**이유**

1. **D-009로 회원가입/로그인이 1차 범위에 들어왔다.** 로그인이 있으면 인증 수단이 필요하다.
2. **SPA + REST에 세션 쿠키를 쓰면 설명이 길어진다** — CSRF 토큰 처리, 쿠키 SameSite 설정이
   따라붙는다. 부킹엔진은 이미 별도 오리진 없이 단일 JAR로 나가지만(D-001),
   REST API의 상태 없음(stateless)을 유지하는 편이 서사가 깔끔하다.
3. **인증 방식이 두 개인 것 자체가 설명 가치가 된다** — "왜 같은 앱에서 백오피스는 세션,
   고객은 JWT인가"는 면접에서 답할 수 있는 질문이다.
   (세션은 서버가 상태를 들고 즉시 무효화할 수 있어 직원 계정에 적합하고,
   JWT는 상태가 없어 고객 트래픽에 유리하되 즉시 무효화가 어렵다.)
4. **비회원 예약 경로는 그대로 남는다.** JWT는 로그인 사용자에게만 추가되는 선택지이고,
   예약번호+전화번호 조회는 인증 없이 계속 동작한다.

**감수하는 대가**

- D-001에서 회피하려던 인증 비용(약 8h)을 다시 진다.
- 토큰 저장 위치(메모리 vs localStorage) 선택과 XSS 노출 논점이 생긴다.
- Spring Security 설정이 두 갈래(세션 체인 + JWT 필터 체인)로 나뉜다.

**폐기한 대안** 부킹엔진 세션 쿠키 — 위 2번 사유.

## D-009. 회원가입/로그인을 1차 범위로 편입 (D-007 부분 supersede)

**결정일** 2026-07-29

**결정** D-007에서 백로그로 뺐던 회원가입/로그인을 1차 범위로 되돌린다.
`member` 테이블은 V1 스키마에 이미 들어가 있다.

**이유**

1. **비회원 예약만 있으면 React 쪽에 보여줄 것이 얇다** — D-001이 React를 택한 근거는
   "프론트가 평가 대상"인데, 로그인·토큰 갱신·인증 상태에 따른 라우팅 분기는
   프론트 역량이 실제로 드러나는 지점이다.
2. **BCrypt 해싱·인증 필터는 백엔드에서도 흔히 묻는 주제다.** 없으면 포트폴리오에 구멍이 된다.
3. 비용 재평가 — D-007 시점에는 "전면 React + 관리자 JWT"를 가정해 8h로 봤다.
   실제로는 고객 로그인 하나이고 권한 체계도 단순해 비용이 그보다 작다.

**감수하는 대가** 1차 범위가 늘어난다. 대신 D-010으로 범위를 좁혀 상쇄한다.

## D-010. JWT는 Access Token 단독 — 리프레시 로테이션은 백로그

**결정일** 2026-07-29

**결정** Access Token 하나만 발급한다(만료 시 재로그인).
Refresh Token 발급·저장·로테이션·재사용 탐지는 구현하지 않는다.

**이유**

1. **리프레시 로테이션을 제대로 하려면 서버 저장소와 재사용 탐지가 필요하다** —
   토큰 저장 테이블, 회전 시 이전 토큰 무효화, 탈취 탐지 시 계정 전체 무효화까지

   보안상 더 나쁘다.
2. **이 프로젝트의 핵심 주제는 동시성·정합성이지 인증이 아니다.** 인증에 시간을 더 쓰면
   핵심 3과제(오버부킹 0건, Hold 만료 복원, 마감 멱등성)가 얇아진다.
3. 재로그인 UX 저하는 데모 범위에서 문제되지 않는다.

**감수하는 대가**

- 토큰 만료 시 사용자가 다시 로그인해야 한다.
- "리프레시 토큰은 왜 없나" 질문에 답할 준비가 필요하다 (위 1번이 답).

**폐기한 대안** Access + Refresh 로테이션 — 위 1·2번 사유. 백로그로 이관.

## D-014. `member` / `staff_user` 테이블 분리

**결정일** 2026-07-29

**이유**

**감수하는 대가**

- 인증 설정이 두 벌 필요하다 (D-008에서 이미 감수하기로 한 비용과 같다).
- 두 테이블에 공통 컬럼(password_hash 등)이 중복된다.

**폐기한 대안** 단일 `user` 테이블 + role 컬럼 — 위 2번 사유가 결정적.

## D-016. SQL 로깅 — Hibernate 내장 (p6spy 미사용)

**결정일** 2026-07-29

**결정** `org.hibernate.SQL: DEBUG` + `org.hibernate.orm.jdbc.bind: TRACE`로 SQL과
바인딩 파라미터를 본다. p6spy(또는 datasource-proxy)를 추가하지 않는다.

**감수하는 대가** 로그가 SQL과 파라미터 두 줄로 나뉘어 p6spy처럼 한 줄 완성 SQL로 보이지 않는다.

## D-018. 재고를 읽는 **첫 조회**가 락 조회여야 한다

**결정일** 2026-07-29 (Day 0 비관적 락 스파이크의 결과)

**결정** 예약 트랜잭션에서 `room_inventory`를 읽을 때, **맨 처음 읽는 쿼리부터**
`FOR UPDATE`여야 한다. "먼저 가용 재고를 조회해 보여주고, 확정 단계에서 락을 잡는다"는
순서를 같은 트랜잭션 안에서 쓰지 않는다.

**이유 — 실측으로 확인했다.** 락을 나중에 거는 코드는 **락을 잡고도 옛 값을 읽는다.**
원인이 두 겹이라 한쪽만 알면 못 막는다.

1. **영속성 컨텍스트(1차 캐시)가 DB 결과를 버린다.** 이미 영속 상태인 인스턴스가 있으면
   JPA는 `SELECT ... FOR UPDATE`를 실제로 보내고 락도 잡지만, DB가 돌려준 최신 행을
   버리고 캐시에 있던 인스턴스를 반환한다. 스파이크에서 `locked.get(0) == inventory`가
   `true`로 찍혔다.
2. **락 없는 읽기는 REPEATABLE READ 스냅샷을 본다.** MySQL 기본 격리수준에서 일반 SELECT는
   트랜잭션이 처음 읽은 시점의 스냅샷을 읽는다. 그래서 `EntityManager.refresh()`로도
   최신 값이 오지 않는다.
3. **`refresh(entity, PESSIMISTIC_WRITE)`로도 회복되지 않았다.** 기대와 달리
   `for update`가 붙지 않은 평범한 `select ... where id=?`가 나갔다(실측).

결과: DB의 실제 `sold_qty`가 2인 동안 트랜잭션 안에서는 네 번의 조회가 모두 1을 반환했다.
이 상태로 재고를 검사하면 **락을 걸었는데도 오버부킹이 난다.** 이 프로젝트의 핵심 주장이
정면으로 무너지는 지점이다.

**어떻게 지킬 것인가**

- 재고 조회 경로를 둘로 분리한다.
  가용 재고 **표시용**(락 없음, 읽기 전용 트랜잭션) / 예약 **확정용**(첫 쿼리부터 `FOR UPDATE`).
- 확정 트랜잭션 안에서는 표시용 조회 메서드를 호출하지 않는다.
- 검증은 Day 2 동시성 통합테스트(D-006)가 맡는다. 오버부킹 0건이 이 규칙의 회귀 테스트다.

**감수하는 대가** 예약 확정 경로에서 재고를 미리 훑어보는 최적화를 쓸 수 없다.
락 범위가 트랜잭션 전체로 넓어져 경합이 커진다 — 그래서 확정 트랜잭션을 짧게 유지해야 한다.

**근거** 스파이크 코드와 실행 로그: `io.github.jeongkyuchoi.hotel.erp.common.support.spike.PessimisticLockSpike`.
실행 방법과 실측 결과는 그 클래스 주석과 커밋 `7a08a53` 메시지에 있다.

## D-019. 엔티티 매핑 공통 규약

**결정일** 2026-07-30

**결정** 모든 엔티티에 다음을 강제한다.

| 항목 | 규칙 | 예외 |
|---|---|---|
| `@ManyToOne` | **항상 `fetch = LAZY`** | 없음 |
| 상태값 | `@Enumerated(EnumType.STRING)` | 없음 |
| 금액 | `BigDecimal` + `precision`/`scale` 명시 | 없음 |
| DB `TINYINT` | 자바 `int` + `@JdbcTypeCode(SqlTypes.TINYINT)` | 없음 |
| 연관관계 | 탐색이 필요하면 `@ManyToOne`, 기록이면 `Long` | `RoomInventory.roomTypeId`(락 경로), `ReservationNight.roomTypeId`(스냅샷 기록) |

**이유**

1. **`@ManyToOne` 의 기본값이 EAGER 다.** 명시하지 않으면 목록 조회 한 번에 연관 테이블
   조회가 건마다 따라붙는다(N+1). 기본값이 위험한 쪽이므로 규약으로 못 박는다.
   대가는 목록 쿼리마다 `join fetch` 를 직접 써야 하는 것이다 —
   `RoomRepository.findAllForList` 가 그 예다.
2. **`EnumType.ORDINAL` 은 enum 상수 순서를 바꾸는 순간 기존 데이터의 의미가 통째로 달라진다.**
   `CANCELLED` 를 목록 중간에 끼워 넣는 흔한 변경이 과거 예약 상태를 전부 밀어버린다.
   스키마도 `VARCHAR + CHECK` 로 잡혀 있어 STRING 과 그대로 맞물린다.
3. **`double` 은 부동소수 오차로 정산이 어긋난다.** 숙박일수만큼 더하는 구조라
   오차가 누적된다.
4. **`TINYINT` ↔ `int` 는 `ddl-auto: validate` 가 기동을 실패시킨다.** 실제로 겪었다.
   자바 타입을 `byte` 로 바꾸는 대안은 인원 계산마다 int 로 승격돼 캐스팅만 늘어난다.

**감수하는 대가**

- 목록 조회마다 `join fetch` 쿼리를 직접 써야 한다(LAZY 의 대가).
- 상태값을 문자열로 저장해 `ORDINAL`(정수)보다 저장 공간을 더 쓴다. 무시할 수준이다.

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| `@ManyToOne` 기본값(EAGER) 사용 | 조용한 N+1. 문제를 발견하기 어렵다 |
| `EnumType.ORDINAL` | 위 2번. 데이터 손상이 조용히 일어난다 |
| 전부 `Long` FK (연관관계 없음) | 백오피스 화면에서 타입 이름을 찍는 것조차 서비스에서 조립해야 한다 |

## D-020. 기준정보는 삭제하지 않고 비활성화한다

**결정일** 2026-07-30

**결정** 객실타입·호실·요금정책에 물리 삭제(DELETE) 기능을 만들지 않는다.
`active` 플래그를 끄는 것으로 대신한다. 목록 화면의 버튼도 "삭제"가 아니라
"판매중단 / 사용중지"다.

**이유**

1. **애초에 지울 수 없다.** 호실·요금정책·재고·예약이 FK 로 참조하고 있어
   DELETE 가 제약 위반으로 실패한다. 되는 것처럼 화면을 만들면 사용자가
   누를 때마다 알아볼 수 없는 예외를 본다.
2. **지울 수 있게 만들면 과거 예약이 무의미해진다.** "2026년 8월에 어떤 객실타입을
   얼마에 팔았는가"를 답할 수 없게 된다. 정산·감사에서 필요한 정보다.
3. **판매 중단은 삭제가 아니다.** 실무에서 필요한 것은 "더 이상 팔지 않는다"이지
   "존재한 적 없다"가 아니다. 비활성화가 요구를 정확히 표현한다.

**감수하는 대가**

- 잘못 만든 데이터가 목록에 계속 남는다. 화면이 지저분해진다.
  → 완화: 정렬에서 뒤로 밀거나 필터를 추가한다(현재는 미구현).
- 코드(`code`)를 재사용할 수 없다. 유니크 제약이 비활성 행에도 걸려 있기 때문이다.

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| 물리 삭제 | 위 1·2번 |
| soft delete 컬럼(`deleted_at`) 추가 | `active` 와 의미가 겹친다. 상태가 둘이면 "비활성인데 삭제 안 됨"이 무슨 뜻인지 답해야 한다 |

## D-021. 운영 상태값은 기준정보 화면에서 편집하지 않는다

**결정일** 2026-07-30

**결정** 업무 흐름이 바꾸는 상태값은 기준정보 폼에서 제외한다.
첫 적용 대상은 `room.occupancy_status`(공실/투숙중)다. 수정 화면에 **표시는 하되
`disabled`** 로 두고, 폼 DTO(`RoomForm`)에 아예 필드를 두지 않는다.

반대로 `room.clean_status`(청결)는 편집을 허용한다.

**이유**

1. **점유 상태는 예약과 체크인/체크아웃이 소유한 값이다.** 기준정보 화면에서 임의로
   `VACANT` 로 되돌릴 수 있으면, 투숙 중인 방에 다른 손님을 배정하는 사고가 난다.
   화면에서 막는 것으로 부족해 **폼 DTO 에 필드를 두지 않는다** — 요청 파라미터를
   직접 만들어 보내도 바인딩될 대상이 없다.
2. **청결 상태는 다르다.** 고장으로 인한 `OUT_OF_ORDER` 처리는 기준정보 담당의 일이고,
   업무 흐름이 자동으로 판단해 주지 않는다.
3. **이 구분이 상태를 2축으로 나눈 설계의 값을 실현한다.** 한 컬럼이었다면
   "고장이면서 투숙중"을 표현할 수 없고, 편집 가능/불가를 나눌 수도 없다.

**적용 범위** 앞으로 만들 화면에도 같은 기준을 적용한다.
`reservation.status`, `reservation_night.posted`, `room_inventory.sold_qty`/`held_qty`
는 전부 업무 흐름이 소유한다. 관리자가 직접 고쳐야 하는 상황이 생기면
그것은 폼이 아니라 **사유를 남기는 별도 기능**으로 만든다.

**감수하는 대가**

- 데이터가 꼬였을 때 화면으로 손볼 수 없어 DB 를 직접 만져야 한다.
  → 그것이 맞다. 손으로 고칠 수 있으면 왜 꼬였는지 아무도 조사하지 않는다.

**폐기한 대안** 전 항목 편집 허용 — 위 1번 사유.

## D-022. 요금 캘린더 생성은 락을 걸지 않는다 (재고 생성과 대비)

**결정일** 2026-07-30

**결정** `rate_calendar` 행을 만들 때, 기존 행을 **락 없는 일반 조회**로 읽어 병합한다.
재고 생성(`InventoryService.generate`)이 첫 조회부터 `lockForUpdateNative`(D-018)로
시작하는 것과 반대다. 구조는 둘 다 "날짜 범위에 행 펼치기"로 같지만 락 정책이 다르다.

**이유**

1. **요금표는 예약 트랜잭션이 동시에 잠그는 행이 아니다.** 예약은 `room_inventory`의
   `sold_qty`/`held_qty`를 올릴 뿐, `rate_calendar`를 건드리지 않는다. 그래서
   "락을 걸었는데 옛 값을 읽는다"(D-018)는 문제가 성립할 경합 상대가 없다.
2. **예약 금액은 확정 순간 `reservation_night`에 스냅샷으로 복사된다.** 요금표를
   나중에 바꿔도 과거 예약 금액이 흔들리지 않는다. 즉 요금표 수정과 예약은 시간적으로
   분리돼 있다.
3. **요금표를 바꾸는 주체는 관리자 한 명(ADMIN 전용 경로)이다.** 관리자 두 명이
   같은 날짜를 동시에 저장하는 드문 경합은 유니크 제약 `uk_rate_calendar`가 막는다.
   비관적 락까지 갈 필요가 없다.

이 대비가 "왜 저기(재고)는 락을 걸고 여기(요금)는 안 거는가"에 대한 답이다.
락은 습관이 아니라 **동시에 같은 행을 놓고 다투는 경합이 있을 때만** 건다.

**감수하는 대가**

- 관리자 두 명이 같은 요금정책·같은 날짜를 밀리초 차이로 동시에 저장하면 나중 것이
  이긴다(last-write-wins). 요금 설정 업무 특성상 문제되지 않는다.

**폐기한 대안** 재고와 동일하게 `FOR UPDATE` — 경합 상대가 없어 락 비용만 늘어난다.

**검증** admin 로그인 후 2026-08-03(월)~08-09(일) 범위에 주중 100,000 / 주말 150,000으로
생성해 주말 2일만 15만원이 적용됨을 확인했다(요일별 차등). 같은 값으로 재생성 시
`생성 0 · 갱신 0 · 유지 7`로 멱등하게 동작하고, STAFF 계정은 이 경로에서 403을 받는다.

## D-023. 예약 HOLD 생성 서비스 설계

**결정일** 2026-07-30

**결정** 예약을 `status=HOLD` 로 만드는 서비스(`ReservationService.hold`)를 다음 규칙으로 짠다.

1. **재고 락 우선(D-018 첫 적용).** 이 트랜잭션에서 재고를 처음 읽는 쿼리가
   `lockForUpdateNative`(FOR UPDATE)다. 표시용 조회(`findRange` 계열)는 부르지 않는다.
2. **연박은 all-or-nothing.** 어느 하루라도 재고가 부족하면 예외로 트랜잭션 전체를
   롤백해 이미 올린 다른 날짜의 `held_qty` 도 되돌린다. 부분 예약은 만들지 않는다.
3. **HOLD TTL = 10분.** 이 안에 결제하지 않으면 스케줄러가 EXPIRED 로 돌리고 재고를
   반환한다(D-003). 조회 시점에는 만료분을 만료로 취급해 지연을 감춘다.
4. **멱등키 선조회.** 유니크 제약이 최후에 막지만, 같은 키의 예약을 먼저 조회해 그대로
   돌려주는 편이 더블클릭·재시도에 대한 사용자 경험이 낫다.
5. **예약번호 = `R`+`yyMMdd`+무작위 4자리.** AUTO_INCREMENT id 를 노출하지 않는다 —
   연속 정수는 열거 공격 표면이다. 혼동 문자(0/O,1/I) 뺀 31자 집합. 충돌은 유니크
   제약+재시도로 막는다.
6. **오버부킹 3중 방어.** 도메인 `RoomInventory.hold`(가용 검사) → DB
   `CHECK(sold+held<=total)` → 이 전체를 감싸는 행 락(D-018). 어느 하나가 뚫려도
   다음이 막는다.

**이유** 화면보다 서비스를 먼저 만들어야 동시성 검증을 화면 너머가 아닌 서비스에서
직접 할 수 있다. HOLD 상태가 임시점유를 겸하므로(D-003) 별도 점유 테이블 없이
`held_qty` 증가만으로 점유가 표현된다.

**감수하는 대가**
- HOLD TTL 10분은 임의값이다. 결제 UX 실측 후 조정할 수 있다.
- 확정 트랜잭션이 재고를 잠근 채 요금표까지 조회하므로 락 보유 시간이 늘어난다.
  요금표 조회는 락 없는 다른 테이블이라 짧고, 확정 로직 자체를 짧게 유지해 상쇄한다.

**검증** Day 2 동시성 통합테스트(D-006, Testcontainers)가 오버부킹 0건으로 이 설계의
회귀 테스트를 겸한다. 단위 흐름은 그 전에 curl/부팅으로 확인한다.

**미구현(후속)** 결제 성공 시 HOLD→CONFIRMED 전이(`confirmHold`), 예약 조회/취소.
도메인 메서드는 `RoomInventory` 에 미리 넣어 두었다.
(HOLD 만료 스케줄러는 D-024 로 구현됨.)

## D-024. HOLD 만료 스케줄러 — 건별 트랜잭션 + 락 후 반환

**결정일** 2026-07-30

**결정** 만료된 HOLD 정리(D-003)를 다음 구조로 구현한다.

1. **건별 독립 트랜잭션.** 스케줄러(`HoldExpiryScheduler`)는 만료 대상 **id 목록만** 뽑아
   루프를 돌고, 예약 한 건의 만료(`ReservationExpiryService.expireOne`)는 각각 별도
   트랜잭션이다. 한 건 실패가 배치를 무너뜨리지 않고, 재고 락 보유 시간도 짧다.
   Spring `@Transactional` 자기호출 문제 때문에 루프(스케줄러)와 건별 처리(서비스)를
   **다른 빈**으로 나눈다.
2. **반환도 재고 락 우선(D-018 재적용).** `releaseHold` 는 `held_qty` 를 내리므로
   새 예약의 `hold`(증가)와 같은 행을 두고 다툰다. 되돌릴 행을 `FOR UPDATE` 로 먼저
   잠근다. 락 없이 하면 갱신 유실로 재고가 어긋난다.
3. **멱등.** `expireOne` 은 로드 후 `isHoldExpired(now)` 로 재확인해, 이미 확정·취소·
   만료됐거나 아직 만료 전이면 아무 것도 하지 않는다. 스케줄러가 겹쳐 돌거나 결제
   확정과 경합해도 재고가 이중 반환되지 않는다.
4. **시각을 파라미터로.** `sweep(now)` 가 시각을 받는다. 스케줄러는 `now()` 를 넘기고
   테스트는 미래 시각을 넘겨, 백데이트 없이 결정적으로 만료를 검증한다.

**감수하는 대가** 스케줄러 주기(1분)만큼 재고 반환이 지연된다. → 가용 재고 조회 시
만료분을 만료로 취급해(D-003) 사용자에게는 지연이 보이지 않는다. 스케줄러는 청소만 한다.

**검증** Day 2 통합테스트(D-006 ②): 2박 HOLD 를 미래 시각으로 청소 →
EXPIRED 전이 + 두 야간 `held_qty` 반환, 재실행 시 0건 처리(멱등), 만료 전 HOLD 는
무변경. 실제 MySQL 에서 통과. 동시성 테스트(D-006 ①)와 함께 회귀 테스트가 된다.

## D-025. 상태 전이는 예약 행 락으로 직렬화 (확정/만료 경합)

**결정일** 2026-07-30

**결정** HOLD 예약의 상태 전이(확정·만료, 이후 취소도)는 **예약 행을 `FOR UPDATE`로
먼저 잠근 뒤** 진행한다(`ReservationRepository.findByIdForUpdate`). 락 순서는 언제나
**예약 → 재고**로 통일한다.

**이유** 결제 확정과 HOLD 만료가 같은 예약을 거의 동시에 건드릴 수 있다(사용자가 만료
직전에 결제). 재고 락(D-018)만으로는 부족하다 — 재고에 여유가 있으면 확정과 만료가 같은
예약 행의 상태를 각자 덮어써(lost update) "EXPIRED 인데 재고는 sold" 같은 불일치가 난다.
예약 행 자체를 직렬화 지점으로 삼으면, 먼저 잠근 트랜잭션이 전이를 끝내고, 뒤이은
트랜잭션은 락 읽기로 **최신** 상태를 보고 자신의 가드로 넘어간다.
- 확정이 이기면: 만료의 `findByIdForUpdate` 가 CONFIRMED 를 읽어 `isHoldExpired=false` →
  무동작(멱등).
- 만료가 이기면: 확정이 EXPIRED 를 읽고, 재고 `confirmHold` 가 held=0 에 걸려 거부 →
  결제는 상위에서 환불로 처리.

**락 순서를 예약 → 재고로 고정하는 이유** 확정·만료 모두 이 순서를 지키면 서로 간
데드락이 없다. 예약 생성(`hold`)은 예약 행이 아직 없어 재고만 잠그므로 이 순서와 충돌하지
않는다.

**감수하는 대가** 전이마다 락이 하나 더 붙어(예약 행) 경합 시 대기가 생긴다. 전이 로직이
짧아 보유 시간은 밀리초 수준이다.

**검증** Day 2 통합테스트(D-025): 재고 1개 HOLD 에 확정과 만료를 동시 실행하는 경합을
8회 반복 → 매번 정확히 하나만 성공(CONFIRMED xor EXPIRED), held=0 유지, 승자에 따라
sold∈{0,1}. 확정 멱등(재확정 시 재고 이중 이동 없음)도 확인. 실제 MySQL 통과.

## D-026. 야간마감 멱등성 — 마감 이력 유니크 + posted 플래그 2중 방어

**결정일** 2026-07-30

**결정** 야간마감(D-004)을 다음 구조로 구현한다. 핵심 기술 과제 ③의 본체다.

1. **마감 이력 테이블 `night_close`(V2) + `UNIQUE (tenant_id, business_date)`.** 영업일당
   마감 이력은 정확히 한 행이다. 이 행의 존재가 "그 영업일은 마감됐다"는 사실이며,
   재마감 INSERT 는 유니크 제약이 거부한다.
2. **게시 = `reservation_night.posted` false→true + 이력 집계.** 폴리오 원장 테이블은
   두지 않는다 — 1차 범위에서 게시는 posted 전환과 마감 집계 기록까지다. 고객 청구서는
   결제·정산 모듈과 함께 후속 범위. 멱등성 증명에는 이 둘로 충분하다.
3. **게시 대상은 CONFIRMED·CHECKED_IN 의 그날 숙박분.** HOLD·EXPIRED·CANCELLED·NO_SHOW 는
   숙박료를 게시하지 않는다.
4. **트리거(스케줄러)와 로직(서비스) 분리** — D-024 와 같은 이유(`@Transactional` 자기호출).
   `NightCloseScheduler.run(businessDate)` 가 시각/영업일을 파라미터로 받아 테스트가
   결정적으로 검증한다. 크론은 03:05 에 직전 영업일을 마감한다.

**멱등성을 두 겹으로 막는 이유** 두 방어선은 다른 층을 막는다.
- **① 유니크 제약(영업일 단위).** 선조회로 이미 마감된 영업일이면 게시 없이
  `alreadyClosed` 를 돌려준다. 두 실행이 동시에 선조회를 통과하는 경합은 유니크 제약이
  최후에 막아 나중 트랜잭션을 통째로 롤백(게시한 posted 전환까지 되돌림)한다.
- **② `posted = false` 필터(숙박분 단위).** 게시 대상 조회가 미게시분만 가져오므로,
  이력 없이 게시 로직만 두 번 돌아도 같은 숙박분이 두 번 게시되지 않는다.
  `ReservationNight.post()` 의 가드가 도메인에서 한 번 더 못 박는다.

**감수하는 대가**
- 동시 마감의 패자는 유니크 위반 예외로 롤백된다. 배치 재실행 맥락에서 문제되지 않고,
  순차 재실행(정상 경로)은 선조회에서 깔끔히 `alreadyClosed` 로 걸러진다.
- NO_SHOW 판정(당일 미투숙 CONFIRMED → NO_SHOW)은 이 범위에 넣지 않았다. 게시 멱등성과
  독립된 관심사라 후속으로 미룬다.

**폐기한 대안** Spring Batch 의 재실행 방지(D-004 참조) · 폴리오 원장 테이블(범위 밖).

**검증** Day 2 통합테스트(D-026, Testcontainers): 2박 CONFIRMED 예약에 D0 마감을 2회 실행 →
1회차 게시 1건, 2회차 `alreadyClosed`·게시 0건, 이력 정확히 1행, D0 posted=true·D1 불변.
HOLD 예약은 게시되지 않음. 동시 실행 8회 반복 → 매번 이력 1행·게시 정확히 1건·실제
마감 성공 1회 이하. 실제 MySQL 통과. 핵심 3과제(오버부킹 0 · HOLD 만료 복원 · 마감 멱등)
완성.

## D-027. 예약 취소 — 직전 상태가 반환 버킷을 결정, 락 순서 예약→재고

**결정일** 2026-07-30

**결정** 예약 취소(`ReservationCancelService.cancel`)를 다음 규칙으로 짠다.
출처 불명으로 폐기했던 `Reservation.cancel()`(핸드오프 §4)을 이 설계로 재작성했다.

1. **되돌릴 재고 버킷은 취소 직전 상태가 결정한다.** HOLD 취소는 `held_qty` 를,
   CONFIRMED 취소는 `sold_qty` 를 반환한다. `cancel()` 이 상태를 CANCELLED 로 바꾸면 직전
   상태가 사라지므로, 서비스가 전이 **전에** 상태를 읽어 버킷을 정한다.
   도메인에 `RoomInventory.releaseSold` 를 `releaseHold` 와 대칭으로 추가했다.
2. **취소 가능 상태는 HOLD·CONFIRMED 뿐.** CHECKED_IN·CHECKED_OUT 은 투숙이 시작/완료돼
   취소가 아니라 다른 업무(중도퇴실·환불)의 영역이고, EXPIRED·NO_SHOW 는 이미 재고를
   점유하지 않아 되돌릴 것이 없다. `cancel()` 도메인 가드가 그 외 상태를 거부한다.
3. **락 순서 예약 → 재고(D-025 재적용).** 예약 행을 먼저 `FOR UPDATE` 로 잠가 확정·만료와
   같은 순서로 직렬화한다. 만료가 먼저면 취소가 EXPIRED 를 읽고 거부되고, 취소가 먼저면
   만료가 CANCELLED 를 보고 무동작한다. 재고 반환은 그 다음 잠근 행에 대고 한다(D-018).
4. **멱등.** 이미 CANCELLED 면 재고를 또 되돌리지 않고 그대로 돌려준다.

**감수하는 대가**
- 위약금(penalty_rate)·환불 계산은 이 범위에 넣지 않았다. 취소는 재고 반환과 상태 전이까지고,
  정산은 결제 모듈과 함께 후속으로 다룬다. `cancel_reason` 만 남긴다.

**폐기한 대안** 재고 반환 없이 상태만 CANCELLED — 되돌리지 않은 held/sold 가 재고를 영구
잠식해 오버부킹의 반대(재고 누수)가 난다.

**검증** Day 2 통합테스트(D-027, Testcontainers): HOLD 취소 → held 반환·취소 메타 기록,
CONFIRMED 취소 → sold 반환, 재취소 멱등(이중 반환 없음), EXPIRED 취소 거부. 동시 이중 취소
8회 반복 → 재고 정확히 한 번만 반환(sold=0). 실제 MySQL 통과.

## D-028. 예약 조회 — 비회원 경로(예약번호+전화), 존재여부 비노출·조회시점 만료표시

**결정일** 2026-07-30

**결정** 비회원 예약 조회(`ReservationQueryService.findForGuest`)를 다음 규칙으로 짠다.

1. **예약번호 + 전화번호 두 키를 함께 요구한다.** 예약번호는 고객 노출값이라 그것만으로
   조회를 열면 남의 예약이 보인다. 전화번호로 소유를 증명한다. 리포지토리 메서드
   `findByTenantIdAndReservationNoAndGuestPhone` 는 이미 있었다.
2. **미존재와 전화 불일치를 구분하지 않는다.** 둘 다 같은 `NotFoundException`. "번호는
   맞지만 전화가 틀렸다"를 흘리면 예약번호 유효성 오라클이 된다. 조회 쿼리가 두 조건을
   AND 로 걸어 구분이 애초에 드러나지 않는다.
3. **엔티티가 아니라 값 뷰(`ReservationDetail`)를 돌려준다.** 지연로딩 연관
   (roomType·ratePlan·nights)을 읽기 전용 트랜잭션 안에서 조립해, 트랜잭션 밖 접근으로 인한
   `LazyInitializationException` 을 원천 차단한다.
4. **표시 상태는 조회 시점 만료를 반영한다(D-003 재적용).** HOLD 인데 `holdExpiresAt` 이
   지났으면 스케줄러 정리 전이라도 EXPIRED 로 보여준다. `ReservationDetail.from(r, now)` 이
   `isHoldExpired(now)` 로 판정한다 — DB 상태는 그대로 두고 표시만 바꾼다.

**감수하는 대가**
- 표시 상태(EXPIRED)와 DB 상태(HOLD)가 잠깐 어긋난다. 의도된 것이다 — 스케줄러가 청소이고
  조회는 지연을 감추는 쪽이다(D-003).
- 회원 로그인 경로(D-009) 조회는 이 범위 밖. 예약번호 없이 내 예약 목록을 보는 경로는
  화면/REST 단계에서 다룬다.

**폐기한 대안** 엔티티 직접 반환 — 지연로딩 예외 + 내부 필드 노출.
예약번호 단독 조회 — 위 1번(소유 증명 부재).

**검증** Day 2 통합테스트(D-028, Testcontainers): 예약번호+전화 일치 시 상세 조립
(연관·2박 야간·총액 200000 포함), 미존재·전화 불일치 모두 NotFound. 조립 로직은 통제된
now 로 만료 전 HOLD / 만료 후 EXPIRED 표시를 직접 검증. 실제 MySQL 통과.

## D-029. 백오피스 예약 목록·상세 — 목록은 fetch join, 상세는 트랜잭션 내 조립

**결정일** 2026-07-30

**결정** 백오피스 예약 화면(`/admin/reservations` 목록, `/admin/reservations/{id}` 상세)을

1. **고객 조회와 서비스를 나눈다.** 직원용 `ReservationAdminService`(인증 세션, 전체

**폐기한 대안** 엔티티를 뷰에 직접 전달 — OSIV 를 껐으므로 렌더링 시점 지연로딩이 예외가

## D-030. 부킹엔진 REST — 가용·HOLD·조회만, 확정은 결제 트리거라 비노출

**결정일** 2026-07-30

**결정** 부킹엔진(`/api`) REST 를 다음 범위·규칙으로 짠다.

1. **엔드포인트는 셋.** `GET /api/availability`(가용 조회) · `POST /api/reservations`
   (HOLD 생성, 201) · `GET /api/reservations/{no}?phone=`(조회). 고객 예약 흐름의 앞단이다.
2. **확정(HOLD→CONFIRMED)은 REST 로 열지 않는다.** 확정의 트리거는 결제 성공이다
   (D-010, D-023). 결제 검증 없는 공개 확정 엔드포인트는 "돈 안 내고 확정"의 구멍이다.
   확정은 결제 모듈의 웹훅이 붙을 때 그쪽에서 노출한다. `ReservationConfirmService` 는
   이미 있으니 배선만 남는다.
3. **가용 조회는 무락 표시 경로(D-018).** `AvailabilityService` 는 읽기 전용 트랜잭션에
   락 없는 조회만 쓴다. 확정 경로의 `lockForUpdateNative` 와 엄격히 분리한다 — 섞이면
   영속성 컨텍스트가 락 조회의 최신값을 가려 오버부킹이 난다(D-018 실측). 가용은
   `총량−확정−점유`(raw)로 계산하고, 만료 HOLD 정밀 차감은 하지 않는다(스케줄러 1분
   주기가 오차 상한, 안전한 방향이라 표시 경로는 raw 로 둔다).
4. **예외 → HTTP 는 `/api` 한정 `@RestControllerAdvice`.** 없음 404 · 재고 부족 409
   (경합의 정상 결과) · 검증 400(필드 메시지 동반). `basePackageClasses` 로 booking
   패키지에만 걸어, 백오피스(HTML·플래시)의 오류 처리를 건드리지 않는다.
5. **요청 검증은 REST DTO(`HoldRequest`)에서.** `@NotBlank`/`@NotNull`/`@Future` 등으로
   막고, 통과분만 서비스 커맨드로 변환한다 — 서비스가 웹 DTO 에 의존하지 않는다.

**감수하는 대가**
- 이 체인은 아직 `permitAll`(JWT 미구현, D-008)이다. **JWT 전에는 외부 노출 금지**
   (핸드오프에도 명시). 조회는 예약번호+전화로 소유만 확인할 뿐 인증은 없다.
- 회원 예약(memberId) 경로는 인증(D-009)이 붙을 때 추가한다. 지금은 비회원만.

**폐기한 대안** 공개 confirm 엔드포인트 — 위 2번(결제 우회 구멍). 전역 예외 어드바이스 —
백오피스 HTML 오류까지 JSON 이 된다.

**검증** Day 2 통합테스트(D-030, MockMvc + Testcontainers): 가용 조회(일자별·bookableQty),
HOLD 생성 201(예약번호·총액 200000), 검증 실패 400(필드 메시지), 재고 부족 409 NO_INVENTORY,
조회 200(전화 일치)/404(불일치). 실제 MySQL 통과.

## D-031. 체크인·체크아웃 — 호실 배정, 락 순서 예약→호실

**결정일** 2026-07-30

**결정** 예약 라이프사이클의 뒷단(CONFIRMED → CHECKED_IN → CHECKED_OUT)을 `StayService` 로
구현한다.

1. **호실은 체크인 시점에 배정한다(D-003 재확인).** 예약은 타입 단위로만 팔리고
   {@code room_id} 는 null 로 두었다가, 체크인 때 그 타입의 <b>배정 가능</b>(활성·공실·
   청소완료/점검완료) 호실을 붙인다. `Room.isAssignable()` 이 기준이다.
2. **락 순서는 예약 → 호실(D-025 규율 확장).** 확정·취소가 예약 → 재고를 지키듯, 체크인은
   예약 행을 먼저 잠가 상태 전이를 직렬화하고, 그다음 호실 행을 `FOR UPDATE` 로 잠가 동시
   배정을 막는다. 두 예약이 같은 호실을 노리면 먼저 잠근 쪽이 `Room.occupy()` 로 OCCUPIED 로
   바꾸고, 뒤이은 쪽은 최신 OCCUPIED 를 읽어 가드에서 거부된다.
3. **재고는 건드리지 않는다.** sold 는 확정 시점에 이미 확정됐다. 체크인은 물리 호실을
   붙일 뿐 재고 수량과 무관하다.
4. **체크아웃은 호실을 DIRTY 로 되돌린다.** 퇴실한 방은 곧바로 재배정하지 않는다 —
   {@code cleanStatus=DIRTY} 로 두어 하우스키핑(1차 범위 밖) 후에야 다시 배정 가능해진다.
   배정 호실({@code room_id})은 지우지 않는다(누가 어디 묵었는지 기록).
5. **상태 전이 가드는 도메인에.** `Reservation.checkIn/checkOut`, `Room.occupy/checkOutVacate`
   가 각자 전제 상태를 검증한다. 서비스는 락·타입 일치·배정 가능만 조율한다.

**감수하는 대가**
- 호실 배정을 직원이 수동 선택한다. 자동배정(층·연박 연속성 최적화)은 후속.
- NO_SHOW 판정(당일 미투숙 CONFIRMED → NO_SHOW)은 여기 없다. 라이프사이클 전이는 갖췄으니
  야간마감에 붙이는 것은 후속 범위다.

**폐기한 대안** 예약 시점 호실 확정 — 연박·타입 재고 모델과 어긋나고, 배정 유연성을 잃는다.
체크인에서 재고 차감 — 이중 차감(확정에서 이미 함).

**검증** Day 2 통합테스트(D-031, Testcontainers): 체크인 → CHECKED_IN·호실 OCCUPIED,
체크아웃 → CHECKED_OUT·VACANT·DIRTY. 확정 아님·타입 불일치·배정 불가 호실 거부. 같은 호실
동시 체크인 8회 반복 → 정확히 하나만 성공. 백오피스 체크인 POST 화면 흐름도 확인. 실제
MySQL 통과.

## D-032. 회원 인증 — JWT Access Token, 필터는 선택 인증, 보호 경로만 401

**결정일** 2026-07-30

**결정** 부킹엔진(`/api`) 회원 인증을 JWT 로 구현한다(D-008, D-009, D-010 실현).

1. **회원가입·로그인.** `POST /api/auth/signup`(BCrypt 해싱, 201) ·
   `POST /api/auth/login`(자격증명 검증 → Access Token). 비밀번호 평문은 서비스에서 즉시
   해싱되고 로그·응답 어디에도 남기지 않는다. `MeResponse` 는 해시를 담지 않는다.
2. **Access Token 단독(D-010).** 리프레시 토큰·저장소·재사용 탐지는 없다. 만료(1h)되면
   재로그인. HS256 대칭키, subject=회원 id, 이메일은 클레임(민감정보는 넣지 않는다 —
   JWT 는 서명될 뿐 암호화되지 않는다).
3. **필터는 선택 인증이다.** `JwtAuthenticationFilter` 는 토큰이 있으면 인증 컨텍스트를
   채우고, 없거나 무효여도 요청을 <b>막지 않는다</b> — 비회원 예약 경로(가용·HOLD·조회)가
   인증 없이 계속 동작해야 하기 때문(D-008). 보호 경로(`/api/me` 등)는 인가 단계에서
   걸러지고 `RestAuthenticationEntryPoint` 가 401 JSON 을 돌려준다(폼 리다이렉트 금지).
4. **인가는 화이트리스트 + 마지막 authenticated.** `/api/auth/**`·`/api/availability`·
   `/api/reservations/**` 만 permitAll, `anyRequest().authenticated()` 로 못 박아 새 API
   경로가 기본 '허용'으로 새지 않게 한다. 핸드오프의 "permitAll 외부노출 금지"를 이로써 해소.
5. **오라클 방지.** 로그인은 이메일 없음·비밀번호 틀림·비활성 계정을 모두 같은
   `UnauthorizedException`(401)으로 던진다. 조회에서 존재 여부를 흘리지 않는 규율(D-028)과
   같은 원칙.
6. **필터를 빈으로 두지 않는다.** `SecurityConfig` 에서 직접 생성해 API 체인에만 끼운다 —
   빈이면 Boot 가 서블릿 필터로도 자동 등록해 모든 요청에 이중으로 돈다.

**감수하는 대가**
- 즉시 무효화가 어렵다(무상태 토큰). 직원 계정은 그래서 세션(D-014). 고객 트래픽은 무상태
  이점이 크고 만료가 1h 라 위험이 제한적이다.
- 회원 예약(memberId 연결)·내 예약 목록은 후속. 지금은 인증 골격과 `/api/me` 까지다.
- JWT secret 기본값은 개발 전용이다. 운영은 `JWT_SECRET` 환경변수 주입 필수.

**폐기한 대안** Access+Refresh 로테이션(D-010, 백로그) · 세션 쿠키(D-008, 무상태 REST 서사
불일치) · 전역 필터 빈(이중 실행).

**검증** Day 2 통합테스트(D-032, MockMvc + Testcontainers): 회원가입 201(해시 미노출),
중복 409, 로그인 200(Bearer·만료 3600), 오비밀번호 401, 토큰으로 `/api/me` 200,
무토큰·무효토큰 401. 기존 부킹 REST(비회원)는 인증 없이 계속 통과. 실제 MySQL 통과.

## D-033. 브랜치 전략 — main(기본·안정) + dev(개발), 배포 시 dev→main

**결정일** 2026-07-30

**결정** 원격 기본 브랜치를 `main`(안정 기준선)으로 두고, 개발은 `dev` 브랜치에 쌓는다.
배포 시점에 `dev → main` 병합한다. 이전의 단일 `feat/init-schema` 브랜치는 폐기했다.

**이유**
1. **`feat/init-schema` 는 이름이 내용과 어긋났다.** "초기 스키마"라는 좁은 기능 브랜치명에
   예약·인증·REST 전체가 담겨 있었다. 기준선/개발선 구분도 없었다.
2. **main 기본 + dev 개발이 표준 구도**라 리뷰어(면접)가 브랜치 전략을 바로 읽는다.
   "완료 후 main 으로"의 실제 모습은 이름 변경이 아니라 `dev → main` 병합이므로 main 이
   처음부터 있어야 서사가 성립한다.

**같이 한 일 (git 위생)** 리포를 삭제·재생성했다. 이유는 별개다 — 깃헙 Contributors 에
Claude 가 계속 뜬 것은 이전 `git filter-branch` 가 남긴 `refs/original` 백업 ref(로컬)와
force-push 로 밀려난 커밋에 대한 깃헙 서버 캐시(원격) 때문이었다. 로컬은 백업 ref 삭제 +
gc 로, 원격은 리포 재생성으로 해소했다(troubleshooting §1). 재생성 리포에 클린 히스토리
(트레일러 0·Claude author 0)만 main·dev 로 올렸다.

**감수하는 대가** 리포 재생성으로 기존 원격 URL 의 히스토리 연속성이 끊긴다(초기 단계라
스타·이슈·PR 이 없어 손실 없음).

**폐기한 대안** `dev` 단독(기본=dev) — main 기준선 부재로 병합 서사가 성립하지 않는다.
`feat/init-schema` 유지 — 이름-내용 불일치.

## D-034. 결제 — 토스 승인이 확정 트리거, 2중 금액검증 + 멱등 + 웹훅 정합

**결정일** 2026-07-31

**결정** 결제 성공을 HOLD → CONFIRMED 확정의 유일한 트리거로 삼고(D-010, D-023, D-030 §2),
토스페이먼츠 승인 API 를 다음 규칙으로 연동한다.

1. **금액 위변조를 두 지점에서 막는다.** 프론트가 보낸 금액은 신뢰하지 않는다. ① 승인 요청
   전, 프론트 `amount` 를 예약 `total_amount`(서버 저장값)와 대조한다 — 결제창 금액 조작으로
   싸게 결제하려는 시도를 막는다(토스 미호출로 조기 거부). ② 토스 승인 응답의 `totalAmount`
   를 다시 저장값과 대조하고 `paymentKey`·`orderId` 반향 일치를 확인한다 — 응답 위조·중간
   변조를 막는다. 시크릿 키는 서버에만 있어(클라이언트로 안 나감) 이 대조가 성립한다.
2. **멱등을 세 겹으로 막는다.** ① 서비스 선조회(`findByPaymentKey`) — 이미 처리된 결제면
   토스를 다시 부르지 않는다. ② `payment.payment_key` UNIQUE — 경합으로 선조회를 놓쳐도
   두 번째 INSERT 를 DB 가 거부한다. ③ `ReservationConfirmService` 자체 멱등 — 이미 CONFIRMED
   면 재고를 두 번 옮기지 않는다(D-025 야간마감 V2 와 같은 두 겹 규율의 확장).
3. **웹훅은 사후 정합이다.** successUrl 콜백이 커밋 전에 끊긴 드문 창을 웹훅이 메운다.
   `DONE` 승인 이벤트만 다루고, 이미 기록된 결제면 무시하며(멱등), 웹훅 금액을 예약 저장값과
   대조해 위조 이벤트로 오확정하지 않는다. 토스에는 항상 200 으로 응답한다 — 4xx/5xx 는
   재전송 폭주를 부른다.
4. **확정 REST 는 결제 모듈에서만 연다.** D-030 §2 의 "확정 비노출"을 이로써 해소한다.
   `POST /api/payments/confirm`(승인 콜백)·`POST /api/payments/webhook` 둘 다 인증 주체가
   없는 경로라 `/api/payments/**` 를 permitAll 로 두고, 보호는 위 금액검증·멱등에 맡긴다.
5. **HTTP 클라이언트는 정적 팩터리로 만든다.** `TossPaymentClient` 는 주입받은
   `RestClient.Builder` 빈에 기대지 않고 `RestClient.builder()` 로 직접 만든다 — 자동구성이
   없는 테스트 컨텍스트에서도 동일하게 동작해야 하기 때문(전체 스위트에서 실측: 주입 방식은
   테스트 컨텍스트 로딩을 전부 깨뜨렸다).
6. **비밀 키는 커밋하지 않는다(D-032 규율 확장).** `app.toss.*` 는 `${...}` 참조만 두고,
   실제 키는 환경변수 또는 gitignore 된 `application-local.yml`(local 프로파일)로 준다.

**감수하는 대가**
- **승인 성공 후 DB 커밋 실패 창.** 토스 승인(네트워크)은 트랜잭션 앞이라, 승인 직후 커밋이
  깨지면 "돈은 나갔는데 미확정"이 된다. 웹훅 정합이 이를 메우나, 웹훅마저 실패하면 수동/배치
  대상이다. 1차 범위의 감수 대가.
- **웹훅 서명 검증 없음.** 서명 검증은 후속 범위. 멱등·금액 대조가 오확정을 막는 최소 방어선.
- **실패 결제 미적재.** 승인 실패는 행으로 남기지 않고 예외로 드러낸다(HOLD 유지 → 만료 회수).

**검증** Day 3 통합테스트(D-034, MockMvc + Testcontainers, 토스 클라이언트만 mock): 정상 승인
200·CONFIRMED·held→sold·결제 1건, 금액 위변조(요청<저장) 400·토스 미호출·HOLD 유지, 응답
금액 위조 400, 멱등 재요청(토스 1회·결제 1건·이중이동 없음), 만료 뒤 도착 409 INVALID_STATE,
웹훅 DONE 정합·재전송 멱등. 전체 스위트 71건 통과, 실제 MySQL.

**폐기한 대안** 확정 공개 REST(D-030 §2 에서 이미 폐기) — "돈 안 내고 확정" 구멍. HOLD 전용
결제대기 테이블 — 예약 자체가 status=HOLD 라 불필요(V1 주석). 주입식 `RestClient.Builder` —
테스트 컨텍스트 파손(위 5).

## D-035. SPA 라우팅 폴백 — 명시 경로만 index.html forward (catch-all 금지)

**결정일** 2026-07-31

**결정** React SPA 의 클라이언트 라우트를 프로덕션에서 살리기 위해, 스프링이 그 경로에
`index.html` 을 forward 하게 한다. 단 **알려진 경로만 명시 등록**하고 광범위 catch-all 은 두지
않는다.

1. **문제.** 배포 시 React 빌드는 jar 의 `classpath:/static` 에서 서빙된다(build.gradle 의
   bootJar 가 `frontend/dist` 를 복사, D-001). 그런데 `/book`·`/payment/success` 같은 클라이언트
   라우트는 대응하는 정적 파일이 없어, 직접 진입·새로고침·결제 리다이렉트가 오면 스프링이
   404(또는 시큐리티에 걸려 302 로그인)를 낸다. dev 에서는 Vite dev server 가 모르는 경로에
   index.html 을 줘서 안 보이던 문제다.
2. **명시 등록만.** `WebMvcConfig` 에 `/book`·`/payment/success`·`/payment/fail` 만
   `forward:/index.html` 로 등록한다. `/` 는 스프링이 static/index.html 을 welcome page 로
   자동 서빙하므로 제외. SPA 라우트가 늘면 여기에 추가한다.
3. **catch-all 금지.** 이 앱은 Thymeleaf 백오피스(`/admin`·`/login`)와 SPA 가 한 서버에
   공존한다(D-001). "무엇이든 index.html 로"류 규칙은 `/admin`·`/api`·`/error`·미등록 경로까지
   삼켜, 백오피스 404 가 React 앱으로 둔갑하는 등 디버깅 지옥을 만든다. 명시 등록이 경계를
   또렷하게 한다.
4. **시큐리티 permitAll.** forward 대상 경로(`/book`·`/payment/**`)를 웹 체인에서 permitAll
   한다 — 아니면 `anyRequest().authenticated()` 에 걸려 로그인으로 튕긴다. 결제 착지는 인증
   주체 없는 공개 경로다. forward 는 query string 을 보존해 결제 파라미터가 유지된다.

**검증** bootJar 를 vite 없이 8080 단독 실행해 실측: `/`·`/book`·`/payment/success?...`·
`/payment/fail` → 200 index.html(쿼리 보존), `/api/room-types` → 200 JSON, `/admin` → 302
로그인, 미등록 `/nonexistent-xyz` → 302(폴백이 삼키지 않음). 전체 스위트 71건 통과.

**감수하는 대가** 새 SPA 라우트마다 `WebMvcConfig`·시큐리티에 한 줄씩 추가해야 한다 —
catch-all 의 편의를 포기한 대가지만, 하이브리드 앱에서 경계 명확성이 그 값을 한다.

**폐기한 대안** 광범위 catch-all forward(정규식 제외 목록) — 백오피스·API 오염 위험(위 3).
프론트를 별도 서버·도메인으로 분리 — CORS 도입·배포 복잡도 증가, D-001 의 "jar 하나" 폐기.

## D-036. NO_SHOW 판정 — 야간마감 뒤 도착일 미투숙 확정분을 전이 (첫날 과금 유지)

**결정일** 2026-07-31

**결정** 도착일에 투숙하지 않은 CONFIRMED 예약을 야간마감(D-026) 직후 NO_SHOW 로 전이한다.
마감 로직은 건드리지 않고 별도 `NoShowService` 로 분리해 스케줄러가 순서대로 부른다.

1. **마감 → NO_SHOW 순서.** `NightCloseScheduler.run` 이 `close()`(그날 밤 숙박분 게시) 뒤에
   `markNoShows()` 를 부른다. 이 순서라야 노쇼 첫날이 게시(과금)된다 — NO_SHOW 는 게시 대상
   상태(CONFIRMED·CHECKED_IN)에서 빠지므로, 전이를 먼저 하면 첫날 과금이 누락된다. 표준
   호텔 노쇼 정책(첫날 과금, 이후 밤 미과금)이 이 순서에서 자연히 나온다.
2. **재고는 되돌리지 않는다.** 취소(투숙 전)는 held/sold 를 반환하지만, 노쇼는 도착일이 이미
   지나 그 밤을 다시 팔 수 없다 — 반환이 무의미하다. 상태만 바꾼다(체크인이 재고를 안
   건드리는 것과 같은 결, D-031).
3. **멱등.** 판정 조회를 CONFIRMED 로 한정한다. 재실행하면 이미 NO_SHOW 인 건은 잡히지
   않는다. 도메인 `Reservation.noShow()` 가드(CONFIRMED 아니면 예외)가 한 번 더 못 박는다.
   마감이 멱등이듯(D-026) 판정도 멱등이라, 크론 중복·재시도에 안전하다.
4. **마감과 분리한 이유.** D-026 은 게시 멱등성의 증명체다. 그 트랜잭션에 NO_SHOW 전이를
   섞으면 검증된 로직이 흐려진다. 트리거(스케줄러)가 두 서비스를 순서대로 부르는 편이 각
   서비스의 책임을 또렷하게 한다(스케줄러/로직 분리 규율의 연장).

**검증** 통합테스트(D-036, Testcontainers): 도착일(D0) 미투숙 확정 → run(D0) 후 NO_SHOW,
그날 숙박분 posted=true(첫날 과금), 다른 날(D1) 도착 확정분은 CONFIRMED 유지;
`markNoShows` 재실행은 0건·상태 불변. 전체 스위트 통과, 실제 MySQL.

**감수하는 대가** 노쇼 첫날 과금을 정책으로 못 박았다 — 무료취소 기한·요금정책별 위약금율
(rate_plan.penalty_rate)을 노쇼에 반영하는 정교한 과금은 후속 범위다. 지금은 "첫날 게시"라는
단순 규칙이다.

**폐기한 대안** NO_SHOW 를 마감 트랜잭션 안에 통합 — D-026 게시 멱등 증명을 흐린다(위 4).
전이 전 재고 반환 — 지난 밤이라 무의미(위 2).


## D-037. 취소·노쇼 위약금 — 순수 정책 계산기 + 예약 스냅샷, 취소·노쇼 통일

**결정일** 2026-07-31

**결정** 취소(D-027)와 노쇼(D-036)의 과금을 요금정책(`rate_plan.refundable`·`cancel_deadline_days`·
`penalty_rate`)으로 계산하는 순수 함수 `CancellationPolicy` 로 통일하고, 확정된 위약금을
예약 행에 스냅샷(`cancellation_fee`·`no_show_fee`)으로 굳힌다.

1. **순수 함수로 분리.** 위약금은 정책·날짜·금액의 함수일 뿐 부작용이 없다. 저장·재고·결제취소
   같은 부작용은 호출자(취소·노쇼 서비스)가 맡고, 계산기는 `quote`(취소)·`quoteNoShow`(노쇼)만
   돌려준다. 반올림(원 단위 HALF_UP)·경계일 같은 까다로운 부분을 실제 MySQL 없이 단위 테스트로
   전 경계 검증할 수 있다. `penalty + refund == total` 불변을 유지한다.
2. **취소 규칙.** ① 환불불가 정책(`refundable=false`) → 위약금 100%. ② 무료취소 기한 이내
   (취소일 ≤ 체크인 − `cancel_deadline_days`) → 위약금 0. ③ 기한 경과 → 총액 × `penalty_rate%`.
   HOLD 취소는 미결제라 위약금 0(`unpaid`). 위약금은 총액을 넘지 않게 클램프한다.
3. **노쇼 = 도착 후 늦은 취소로 통일.** `quoteNoShow` 는 취소와 같되 **무료취소 기한 분기만 없다**
   — 노쇼는 이미 도착일이 지나 무료 구간에 해당할 수 없다. 환불불가는 전액, 그 외는
   `penalty_rate%`. `deadline_days=0` 정책이어도 노쇼는 과금된다(취소라면 당일 무료).
4. **스냅샷으로 굳힌다.** 요금정책이 나중에 바뀌어도(RatePlan.update) 이미 물린 위약금은 변하면
   안 된다 — `reservation_night` 가 예약 시점 요금을 스냅샷하는 규율(D-005)과 같다. 취소 직전
   상태(`prior`)를 상태 전이 전에 읽어 반환 버킷(held/sold)을 정하는 D-027 규율은 유지한다.
5. **야간마감은 건드리지 않는다.** 노쇼 첫날 폴리오 게시(D-026·D-036)는 그대로 두고, 정책상
   위약금은 별도 스냅샷으로만 기록한다. 게시액(reservation_night.posted)과 위약금 스냅샷의
   정합은 정산(폴리오, 후속 범위)이 맞춘다 — 검증된 핵심 과제 ③(마감 멱등)을 흐리지 않는다.

**검증** 단위테스트 `CancellationPolicyTest`(Spring 없이): 환불불가/무료/경계일/기한경과/원단위
반올림/100% 클램프 + 노쇼(환불불가·rate%·무료구간없음). 통합테스트: 확정 취소가 위약금을
예약에 저장·반환, HOLD 취소 0, 노쇼 환불불가 전액 저장·penalty_rate 0 은 0. 전체 스위트 88건
통과, 실제 MySQL. 마이그레이션 V4(cancellation_fee)·V5(no_show_fee).

**감수하는 대가** 실제 환불 실행(토스 결제취소 API)은 후속 범위 — 여기서는 "얼마를 물리고
돌려줄지"의 판정·기록까지만 한다. 노쇼 위약금이 `penalty_rate` 를 따르므로, 첫날 게시액과
위약금이 다를 수 있다(정산이 조정할 몫). 웹 UI 노출은 백오피스 취소 플래시(위약금·환불액)만.

**폐기한 대안** 위약금을 취소/노쇼 서비스 안에서 직접 계산 — 반올림·경계 테스트가 DB 통합
테스트에 묶여 느리고 취약. 노쇼 전용 위약금 규칙을 따로 세우기 — 취소와 어긋나 유지보수
부담(위 3, 통일). 야간마감 첫날 게시를 위약금으로 대체 — 검증된 멱등 로직을 건드림(위 5).


## D-038. 폴리오(청구서) — 읽기 시점 조립형, 상태별 청구액 규칙

**결정일** 2026-07-31

**결정** 예약 한 건의 청구·결제·잔액을 새 원장 테이블 없이 `FolioService` 가 읽기 시점에
조립한다. 청구액은 예약 상태가 정한다.

1. **조립형 (물질화 아님).** 금액의 원본은 이미 `reservation_night.rate_amount`·`reservation.
   cancellation_fee`/`no_show_fee`(D-037)·`payment.amount` 에 있다. `folio_line` 같은 원장
   테이블을 두면 같은 금액이 두 곳에 살아 정합 부담이 생긴다. 그래서 읽을 때 합산하는 뷰로
   두어 단일 진실원천을 지킨다. 부작용이 없어 읽기 전용 트랜잭션에서 지연로딩 접근으로 조립을
   끝낸다. 불변식 `chargeTotal − creditTotal == balance`.
2. **상태별 청구액.** 진행/완료(HOLD·CONFIRMED·CHECKED_IN·CHECKED_OUT)는 숙박료 일자별 합,
   취소는 `cancellation_fee`, 노쇼는 `no_show_fee`, 만료는 0. **취소·노쇼는 total 이 아니라
   위약금을 청구로 본다** — "정책상 받을 금액"을 진실로 삼아, 야간마감의 첫날 posted 게시와
   어긋나는 부분(D-037 §5)을 청구서 층에서 단순화한다. 결제는 APPROVED 결제 합.
3. **만료 시각 지난 HOLD 는 EXPIRED 로 본다.** 스케줄러 청소 전이어도 표시상 EXPIRED 라
   청구 0 이다(회원 목록 MyReservationSummary·비회원 조회 D-028 과 같은 규율). 이 통일이
   없으면 목록은 "만료됨", 청구서는 "미수"로 어긋난다(라이브 검증에서 실제로 잡은 불일치).
4. **노출 백오피스 + 고객 둘 다.** 백오피스 예약 상세에 청구서 패널, 고객은 인증 경로
   `GET /api/me/reservations/{no}/folio`(회원 소유 검증) + React '내 예약' 청구서 토글.
   소유 불일치는 미존재와 같은 NotFound 로 가려 예약번호 오라클을 막는다(D-028 규율).

**검증** 통합테스트 `FolioTest`(Testcontainers): 확정 완납(PAID)·무료취소 후 환불대상
(REFUND_DUE)·노쇼 위약금 완납(PAID)·HOLD 미수(OUTSTANDING)·비회원 예약 소유거부. 전체 스위트
93건 통과, 실제 MySQL. 라이브: 회원 로그인→내 예약→청구서 렌더링, 만료 HOLD 정합 확인.

**감수하는 대가** 수기 부대비용(미니바·조식 추가) 항목은 없다 — 전용 장부(folio_line)가
필요하므로 후속. 실제 환불 실행(토스 결제취소)도 후속 — 여기선 "환불 대상 −N원" 판정·표시까지.
조립형이라 매 조회 시 재계산하지만, 예약 단위 데이터가 작아 비용이 무시할 만하다.

**폐기한 대안** `folio + folio_line` 물질화 원장 — 이중 저장 정합 부담 + 야간마감 게시 로직까지
손봐야 함(위 1). posted 숙박분 합을 청구액으로 — 취소·노쇼에서 위약금과 어긋난다(위 2).


## D-039. 환불 실행 — 백오피스 수동 트리거, 토스 부분취소, 성공 후 원장 반영

**결정일** 2026-07-31

**결정** 폴리오 잔액이 환불 대상(REFUND_DUE)인 예약에 대해, 직원이 백오피스에서 수동으로
환불을 실행한다. 돌려줄 금액만큼 토스 결제취소 API 를 부르고 결제 행에 취소액을 누적한다.

1. **수동 트리거(백오피스 버튼).** 환불은 실제 돈이 나가는 비가역 동작이라 사람이 확인 후
   실행하는 편이 안전·감사에 맞다. 청구서 패널에 환불 대상일 때만 '환불 실행' 버튼을 노출하고
   확인 다이얼로그를 둔다. (버린 대안: 취소 시 자동 환불 — 토스 장애가 취소까지 막고, 실수
   환불을 되돌리기 어렵다.)
2. **환불액은 폴리오가 정한다.** 돌려줄 금액 = {@code −balance} = 유효 결제액 − 청구액.
   위약금(D-037)이 있으면 그만큼 남기는 부분환불이 된다. 토스 부분취소({@code cancelAmount})를
   쓴다 — 전액 취소가 아니라 "취소 누적액"으로 기록한다.
3. **토스 성공 후에만 원장 반영.** 결제취소 API 가 성공한 뒤 {@code payment.canceled_amount}
   를 올린다. 실패하면 PaymentException 으로 트랜잭션이 롤백되어 실제 돈과 장부가 어긋나지
   않는다(결제 승인이 확정 앞에 서는 D-034 와 대칭).
4. **멱등.** 환불 후 잔액이 0 이 되므로 재실행하면 "돌려줄 것 없음"으로 무동작한다. 이미
   환불된 만큼은 {@code effectiveAmount}(= amount − canceled)가 줄어 다시 취소되지 않는다.
   {@code canceled_amount == amount} 면 결제를 CANCELED 로 올린다(완전 취소).
5. **폴리오가 자동 반영.** 폴리오(D-038)의 대변을 {@code effectiveAmount} 로 바꿔, 환불하면
   대변이 줄고 잔액이 0 으로 수렴한다 — 환불 전용 표시 로직을 따로 두지 않는다.

**검증** 통합테스트 `RefundTest`(토스 취소 API 만 mock): 노쇼 위약금 30% → 부분환불(14만,
결제 APPROVED 유지)·무료취소 → 전액환불(20만, CANCELED)·재환불 무동작(토스 1회)·완납 무동작
(토스 미호출). V6 마이그레이션(canceled_amount·canceled_at). 전체 스위트 97건 통과, 실제 MySQL.

**감수하는 대가** 실 토스 환불 end-to-end 는 테스트키로만(자동 스위트는 mock). 부분환불 대상
결제 선택은 승인 결제 순으로 단순 배분한다 — 예약당 승인 결제 1건(uk_payment_order)이라 실질
단일 결제다. 환불 사유 코드 체계·부분환불 이력 상세 노출은 후속.

**폐기한 대안** 취소 시 자동 환불 — 비가역 동작에 사람 확인이 없고 토스 장애가 취소를 막음
(위 1). 별도 refund 테이블 — 결제당 취소 누적액으로 충분하고 payment 와 이중 관리 부담(위 2).


## D-040. 하우스키핑 — 청소 3단계(DIRTY → IN_PROGRESS → CLEAN), 호실 락 전이

**결정일** 2026-07-31

**결정** 체크아웃이 남긴 DIRTY 호실을 청소 흐름으로 흘린다: DIRTY(청소필요) →
IN_PROGRESS(청소중) → CLEAN(청소완료). 백오피스 현황판에서 직원이 시작·완료를 처리한다.

1. **3단계(청소중을 둔다).** 2단계(DIRTY→CLEAN)면 진행 중인 방을 구분 못 해 두 직원이 같은
   방을 잡거나 현황판에서 무엇이 청소 중인지 안 보인다. IN_PROGRESS 를 둬 진행을 드러낸다.
   OUT_OF_ORDER(고장·점검)까지는 이번 범위 밖 — 재고·배정 연계 설계가 필요하다.
2. **CleanStatus 확장 + CHECK 갱신.** enum 에 IN_PROGRESS 를 더하고 V7 로 room.clean_status
   CHECK 제약에 값을 추가한다(MySQL 은 CHECK 수정 불가라 드롭 후 재생성). 기존 값은 그대로.
3. **전이는 호실 행을 잠그고 한다(D-031 규율 연장).** 청소 완료와 체크인 배정, 두 직원의 동시
   처리가 같은 호실 행을 다툴 수 있어 {@code FOR UPDATE} 로 직렬화한다. 상태 가드는 도메인
   ({@code Room.startCleaning}·{@code finishCleaning})이 못 박아, 청소필요 아닌데 시작·청소중
   아닌데 완료를 거부한다.
4. **완료 = 다시 배정 대상.** finishCleaning 이 CLEAN 으로 올리면 {@code isAssignable}
   (활성·공실·청소완료/점검완료)를 다시 만족해 체크인 배정 후보로 돌아온다. 라이프사이클이
   체크아웃 → 청소 → 재배정으로 닫힌다.

**검증** 통합테스트 `HousekeepingTest`(Testcontainers): DIRTY→IN_PROGRESS→CLEAN 전이·완료 후
isAssignable·상태 가드(비DIRTY 시작 거부·비진행 완료 거부)·현황판은 청소필요/청소중만. 전체
스위트 101건 통과, 실제 MySQL. 라이브: 백오피스 로그인 → 하우스키핑 현황판 렌더 확인.

**감수하는 대가** 청소 담당자 배정·소요시간·점검(INSPECTED) 단계는 없다 — 현황판은 상태와
시작/완료 액션까지다. OUT_OF_ORDER 는 기준정보 화면에서 수동 지정만(D-031 Room.update).

**폐기한 대안** 2단계(DIRTY→CLEAN) — 진행 중 방 구분 불가(위 1). 청소 상태를 기준정보 수정
화면에만 두기 — 일상 운영 동선과 안 맞고 상태 가드가 없다.


## D-041. 웹훅 위조 방어 + 환불 동시성 — 재조회 검증, 결제 행 락

**결정일** 2026-07-31

**결정** D-034·D-039 에서 후속으로 미뤘던 두 갭(웹훅 서명 검증 없음 · 환불 락 없음)을 닫는다.

1. **웹훅은 재조회로 검증한다(HMAC 서명 아님).** `/api/payments/webhook` 은 인증 주체가 없는
   공개 경로라 위조 이벤트를 아무나 보낼 수 있다. 토스 결제상태 웹훅은 HMAC 서명을 기본
   제공하지 않으므로, 본문의 금액·상태·주문번호를 믿지 않고 본문의 `paymentKey` 로 토스에
   결제를 <b>다시 조회</b>(`GET /v1/payments/{paymentKey}`, 시크릿 키 인증)해 권위 응답으로
   정합한다. 위조 웹훅은 실재하지 않는 키라 조회가 실패(예외)해 걸러지고, 조작된 금액·상태는
   권위 응답에 없어 오확정되지 않는다. 본문 `status` 는 값싼 사전 필터로만 써 불필요한 조회
   API 호출을 아낀다. 재조회 응답은 승인 응답과 필드 모양이 같아 `TossConfirmResponse` 를
   재사용한다.
2. **재조회는 이미 가진 시크릿 키만 쓴다.** HMAC 방식은 대시보드 웹훅키 발급·주입·관리라는
   새 비밀·새 설정을 요구하고, 계정·이벤트 유형별로 서명 제공 여부가 갈린다. 재조회는 그런
   전제 없이 D-032 비밀 관리 규율에 그대로 얹히고, 승인 콜백이 끊긴 창(D-034 감수 대가)까지
   더 튼튼히 메운다.
3. **환불은 결제 행 락으로 직렬화한다(D-025 규율 연장).** `RefundService`(D-039)만 락 없이
   폴리오·결제를 읽고 취소해, 동시 환불 둘이 같은 `balance<0` 을 보고 둘 다 토스 취소를 부르는
   이중 환불 여지가 있었다(멱등은 순차 재요청만 막음). 이제 `refund()` 진입 즉시 결제 행을
   `FOR UPDATE`(`findByReservationIdForUpdateOrderByApprovedAt`)로 잠근다 — 뒤 트랜잭션은 앞이
   커밋한 갱신된 `effectiveAmount` 를 읽어 잔액 0(이상)을 보고 무동작한다. 취소·확정이 예약 행
   락으로 전이를 직렬화하는 것과 대칭(락 순서 규율 유지).

**검증** 통합테스트: `PaymentApiTest` 웹훅 DONE→재조회로 확정·재전송 멱등, <b>위조 웹훅→재조회
실패로 확정 안 됨·결제 0건·HOLD 유지</b>. `RefundTest` `@RepeatedTest(8)` 동시 이중 환불→토스
취소 정확히 1회·취소액 전액 1회. 전체 스위트 110건 통과, 실제 MySQL.

**감수하는 대가** 웹훅마다 토스 조회 API 를 1회 더 부른다(웹훅은 드물어 부담 없음). 실 토스
end-to-end 재조회는 테스트키로만(자동 스위트는 mock). 환불·취소 행위자 기록과 부분환불 이력은
여전히 후속 범위(핸드오프 3번).

**폐기한 대안** HMAC 서명 검증 — 새 웹훅키 발급·관리 부담, 이벤트 유형별 서명 제공 불확실(위 2).
환불 멱등만으로 방어 — 순차 재요청만 막고 동시 요청은 못 막음(위 3).


## D-042. 환불 이벤트 원장 + 취소 행위자 — 개별 이력을 append-only 로 남긴다

**결정일** 2026-07-31

**결정** "누가·언제·얼마·왜" 환불·취소했는지 감사 이력을 남긴다. D-039 는 잔액 계산용 누적
총액만 남겨(로그 외 개별 이벤트 없음) 이 축이 비어 있었다.

1. **환불은 이벤트 원장(payment_cancel)에 append-only 로 쌓는다.** 환불 실행 한 번 = 한 행
   (payment_id·reservation_id·cancel_amount·reason + 감사컬럼). `payment.canceled_amount`(누적
   총액)는 그대로 유지하고 — 폴리오·멱등이 이 값을 쓴다(D-038·D-039) — 원장은 그 누적을 개별
   이벤트로 <b>분해</b>해 보존한다. 부분환불을 여러 번 해도 각 건이 남는다. 원장 합 = 누적액.
2. **행위자·시각은 기존 JPA 감사를 재사용한다.** `PaymentCancel` 은 {@code BaseEntity} 를 상속해
   `created_by`(로그인 직원명 또는 배치·비인증의 SYSTEM)·`created_at` 이 `AuditorAware` 로 자동
   기록된다(JpaAuditingConfig). 별도 행위자 배선을 만들지 않는다. append-only 라 정정하지 않는다.
3. **취소 행위자는 예약에 못박는다(cancelled_by).** `Reservation.cancel(reason, fee, actor)` 로
   취소 시점에 굳힌다 — `updated_by`(마지막 수정자)와 달리 이후 수정에 덮이지 않는다. 행위자는
   취소 서비스가 같은 `AuditorAware` 로 뽑아 넘긴다(도메인은 SecurityContext 를 모른다). 노쇼는
   취소가 아니라 별도(배치, SYSTEM)이므로 이 컬럼을 쓰지 않는다.

**검증** 통합테스트: `RefundTest` — 부분환불 후 원장 1행(금액·payment_id·created_by=SYSTEM),
멱등 재요청은 원장에 이벤트를 더 쌓지 않음(1행 유지). `ReservationCancelTest` — 취소 후
`cancelled_by`=SYSTEM. V8 마이그레이션(payment_cancel + reservation.cancelled_by). 전체 스위트
110건 통과, 실제 MySQL.

**감수하는 대가** 원장·누적액 두 곳을 함께 갱신한다(한 트랜잭션이라 어긋나지 않음). 부분환불
사유 코드 체계·백오피스 이력 화면 노출은 후속 — 원장은 조회 리포지토리
(`findByReservationIdOrderByCreatedAt`)까지만 깔았다. 취소 행위자는 컬럼 하나로, 취소 이력의
개별 이벤트화(여러 번 상태를 오가는 경우)는 범위 밖(취소는 종단 전이라 1회).

**폐기한 대안** D-039 의 "누적 총액으로 충분" — 잔액엔 맞지만 개별 이벤트·행위자가 없어 감사
불가. 이번에 요구가 바뀌어(누가·언제·개별 이벤트) 원장을 신설해 그 판단을 갱신한다. 취소
행위자를 updated_by 로 갈음 — 이후 수정에 덮여 취소자 보존이 깨짐(위 3).


## D-043. HOLD 만료 표시 규칙을 도메인 메서드로 통합

**결정일** 2026-07-31

**감수하는 대가** 없음(동작 불변). 표시 규칙이 더 복잡해지면(예: NO_SHOW 표시 파생) 같은
메서드를 확장한다.


## D-044. 하우스키핑 4단계 — 점검(INSPECTED) 추가, 배정·재고 연계는 후속

**결정일** 2026-07-31

**결정** 청소 흐름에 점검 단계를 더해 4단계로 만든다: DIRTY → IN_PROGRESS → CLEAN →
INSPECTED. `Room.inspect()`(CLEAN → INSPECTED, 가드)와 현황판 "점검 완료" 액션을 추가한다
(D-040 의 락+가드 패턴 연장).

1. **점검은 배정 게이트가 아니다(이번 범위).** `isAssignable` 은 그대로 CLEAN·INSPECTED 를
   모두 배정 대상으로 본다 — 점검은 운영상 최종 확인일 뿐, 청소완료만으로는 못 팔게 막지
   않는다. "점검해야 판매 가능"으로 배정을 조이는 것은 재고·배정 연계가 필요해 후속 업그레이드
   (A)로 남긴다. **포트폴리오 범위라 상태 흐름만 닫고 불변식(오버부킹 0)은 건드리지 않는다.**
2. **현황판은 파이프라인 전체를 보인다.** 처리 대상 = 청소필요·청소중·<b>점검대기(CLEAN)</b>.
   점검완료(INSPECTED)면 파이프라인을 벗어나 현황판에서 빠진다. 그래서 `findForHousekeeping`
   에 CLEAN 을 더했다 — 청소를 마친 방이 "점검대기"로 남아 관리자가 점검 확인할 때까지 보인다.
3. **사용불가(OUT_OF_ORDER)는 이번에도 손대지 않는다.** 값·라벨은 이미 있고, 지정은 기준정보
   호실 수정에서 수동으로만(D-031, D-040). 현황판 전용 고장 처리·재고 차감은 후속(A·B).

**검증** 통합테스트 `HousekeepingTest`: 4단계 전이(…→CLEAN→INSPECTED)·점검완료도 배정 대상·
점검 가드(청소완료 아닌데 점검 거부)·현황판은 청소필요/청소중/점검대기만(점검완료·사용불가 빠짐).
전체 스위트 112건 통과, 실제 MySQL.

**감수하는 대가** CLEAN 이 "배정 가능"이면서 동시에 "점검대기"로 현황판에 뜨는 이중성 — 점검을
배정 게이트로 삼지 않기로 한 이번 범위의 자연스러운 결과다. 시드된 기존 CLEAN 호실도 한 번은
점검 대상으로 뜬다. 이를 없애려면 점검을 배정의 전제로 올려야 하는데(A), 그건 재고·배정 연계와
함께 갈 후속이다.

**폐기한 대안** 점검을 배정 필수 게이트로(isAssignable=INSPECTED only) — 오버부킹 0 불변식·체크아웃
흐름·다수 시드 가정을 건드려 "작게"에 어긋남(위 1, 후속 A). 점검만 도메인에 넣고 현황판 미노출 —
액션 진입점이 없어 기능이 死藏된다(위 2).

## D-047. 예약 이메일 알림 — 이벤트 + AFTER_COMMIT + EmailSender 추상화

**맥락** 홀딩·확정·취소 시 고객에게 알림이 필요하다. 도메인 서비스에 메일 전송을 직접 넣으면
전송 실패가 예약 트랜잭션에 얽히고, 실 SMTP 계정 없는 데모에서 동작시킬 수 없다.

**결정** 도메인은 이벤트만 발행하고, `@TransactionalEventListener(AFTER_COMMIT)` 리스너가 커밋 후
예약을 재로드해 발송한다 — 롤백된 예약엔 안 나가고, 메일 실패는 삼켜 본 흐름에 영향 없다. 전송은
`EmailSender` 인터페이스 뒤로 숨겨 데모는 `LogEmailSender`(로그), 실 발송은 프로파일 교체로 켠다.
동기 직접호출이 아니라 이벤트 방식을 택해 결합을 끊었다.

**검증** HOLD 생성→홀딩메일, 실결제→확정메일, 확정취소→취소/환불메일(위약금·환불액은 판정값 동봉,
HOLD 는 환불0). 메일실패 0, 기동에러 0.

## D-048. 시각 의존 로직 테스트 가능화 — Clock 빈 주입 (D-045 후속)

**맥락** 당일 예약 마감(D-045)이 `LocalDate.now()`/`LocalTime.now()` 벽시계를 코드에 직접
박아, "지금"에 의존하는 경계(마감 직전 허용 / 직후 차단)를 결정론적으로 테스트할 수 없었다.
CI 가 도는 시각에 따라 결과가 흔들리는 잠재적 flaky 원인이기도 했다.

**결정** `Clock` 을 빈(`ClockConfig#clock`, 기본 `systemDefaultZone`)으로 두고 `ReservationService`
가 주입받아 `now(clock)` 로 읽는다(hold 만료시각 포함 3곳). 테스트는 고정/가변 Clock 을
`@Primary` 로 갈아끼워 경계를 재현한다. 시각 의존 신규 로직은 앞으로 이 패턴을 따른다.

**검증** `SameDayCutoffTest`(신규): 고정 Clock 으로 마감(20:00) 전 허용 · 후 차단 · 후라도
미래일 허용. 전체 스위트 그린(115 tests). 회귀였던 maxOccupancy 픽스처 2건도 함께 수정.

## D-049. 대시보드 실적 KPI — 게시대상 상태 기준 + 세 지표 분자/분모 일관성

**맥락** 백오피스 대시보드에 운영 카운트(도착·재실 등)는 있었으나 매출·가동률·ADR 같은
비즈니스 지표가 없었다. 이 지표들은 "무엇을 판매로 볼 것인가"에 따라 값이 달라진다.

**결정** 오늘 밤 실제로 묵는 예약, 즉 `CONFIRMED`·`CHECKED_IN` 숙박분만 실적으로 센다 —
야간마감 게시대상(D-026)과 같은 상태 규율. HOLD·취소·노쇼는 매출이 아니다. 매출=숙박분
요금 합(ReservationNight), OCC=판매객실/총객실(RoomInventory.totalQty), ADR=매출/판매객실.
세 지표가 **같은 판매객실 수를 공유**하게 해 OCC 분자와 ADR 분모가 어긋나지 않게 했다.
집계는 `Object[]`+coalesce 대신 `RoomRevenueStat` 생성자 프로젝션으로 타입 안전하게 받는다.

**검증** DashboardKpiTest — 확정 1건(1/5실 → OCC 20.0·ADR 20만·매출 20만), HOLD 제외(모두 0),
`/admin` 화면이 KPI 섹션까지 렌더. 전체 118 tests 그린.

## D-050. 다국어(한/영) — 라이브러리 없이 사전+컨텍스트

**맥락** 부킹엔진에 한/영 전환이 필요했다. react-i18next 같은 라이브러리는 기능이 풍부하나
데모 규모엔 과하고 번들·러닝코스트가 붙는다.

**결정** 의존성 없이 `messages.js`(중첩 사전) + `I18nContext`(useI18n, `t(key, vars)`)로 직접
구현한다. 언어는 localStorage 저장·`<html lang>` 동기화·브라우저 언어 폴백. `{name}` 자리표시자
치환만 지원하고 복수형·날짜포맷 같은 고급 기능은 필요할 때 도입한다. 셸+홈을 먼저 덮고 콘텐츠
본문 페이지는 점진 확장한다 — 전면 전환을 한 번에 하지 않는다.

**검증** EN 전환 시 네비·히어로·푸터 번역, `<html lang>`·localStorage 반영. vite 빌드 무에러.

## D-051. 객실타입·요금정책 표시명 다국어 — DB 컬럼(name_en) + 폴백

**맥락** D-050 이후에도 예약 퍼널에 객실명·요금제명이 한글로 남았다(예: 영어 화면의
"기본요금", "스탠다드 트윈"). 이들은 API 가 준 기준데이터라 프론트 사전(t())으로 덮기
어렵다. 프론트에 코드→영문명 매핑을 하드코딩하는 방법도 있었으나, 새 요금제·객실타입이
생길 때마다 코드를 고쳐야 하고 데이터와 표시가 두 곳으로 갈린다.

**결정** 표시명 다국어를 **데이터 계층**에서 푼다. `room_type`·`rate_plan` 에 `name_en`
컬럼을 두고(V10), PMS 등록/수정 화면에서 한글명과 함께 입력한다. API(RoomTypeSummary·
RatePlanSummary)와 예약 DTO(MyReservationSummary·ReservationDetail)가 `nameEn` 을 함께
내려주고, 부킹엔진은 `pickName(lang, name, nameEn)` 으로 고른다. **`name_en` 은 nullable —
비면 한글 `name` 으로 폴백**하므로 기존 데이터·미입력분이 깨지지 않는다. 프론트의 임시
코드 매핑(room.name.*)은 제거하고 이 단일 소스로 통일했다.

마이그레이션 V10 은 컬럼 추가 후, 코드가 고정된 시드 기준데이터(STDT/DLXD/EXSU·요금제 6종)의
영문명을 `name_en IS NULL` 인 행에만 백필한다 — 이미 시딩된 데모 볼륨에서도 영문이 바로
뜨게 하되 관리자가 직접 넣은 값은 덮지 않는다. 언어가 2개라 컬럼 방식으로 충분하며, 3개
이상으로 늘면 별도 번역 테이블로 간다.

**검증** 전체 백엔드 스위트 그린(Flyway V10 검증 포함). API 가 nameEn 반환 확인
(`Standard Rate`·`Standard Twin`). 부킹엔진 EN 모드에서 홈 카드·예약 폼·BookingPage 요금제·
예약 조회/내 예약이 영문, KO 모드에서 한글 폴백까지 dev 실측. vite 빌드 무에러.

## D-052. 객실 이미지 최대 3장 — 컬럼 3개 + 부킹엔진 캐러셀 폴백

**맥락** 객실 상세 갤러리를 프론트 번들 자원으로만 큐레이션하고 있어, 실제 객실 사진을
운영자가 바꿀 수 없었다. 객실별 이미지를 PMS 에서 관리하고 부킹엔진에서 좌우로 넘겨
보게 해야 했다.

**결정** `room_type` 에 `image_url2`·`image_url3` 를 더해(V11) 기존 `image_url`(1번)과 함께
**최대 3장**을 둔다. 전용 이미지 테이블 대신 컬럼 3개 — 상한이 고정이라 부킹엔진·PMS 폼이
단순해진다(가변이 되면 room_type_image 테이블로 분리). PMS 객실 등록/수정 폼에 이미지 3칸,
`RoomTypeSummary` 가 빈 값을 제외한 `imageUrls` 리스트를 노출한다. 부킹엔진 RoomsPage 는
대표사진 캐러셀(좌우 ‹ › 순환·닷·썸네일·라이트박스)로 보여주되, **DB 이미지가 있으면 우선,
비면 기존 번들 큐레이션으로 폴백**(D-051 과 같은 폴백 규율). 데모 시드는 이미지 URL 을 비워
두므로 큐레이션 폴백이 뜨고, 운영자가 URL 을 넣으면 그 이미지로 대체된다.

**검증** 전체 백엔드 스위트 그린(Flyway V11 검증). API `imageUrls` 노출 확인, STDT 에 URL 2장
주입 시 부킹엔진이 그 2장을 캐러셀로(닷 2개) 표시하고 비우면 폴백(닷 4개)으로 복귀함을 dev
실측. 좌우 버튼 순환·썸네일 동기화·라이트박스·vite 빌드 무에러.

## D-053. 객실 이미지 직접 업로드 — 로컬 볼륨 저장 + 서빙(추후 오브젝트 스토리지 이전)

**맥락** D-052 로 객실 이미지 컬럼(최대 3장)은 생겼으나 값은 URL 텍스트 입력이었다. 운영자가
실제 사진 파일을 PMS 에서 바로 올리게 해야 했다. 저장 위치가 관건 — 오브젝트 스토리지(R2/S3)는
내구성이 좋지만 계정·카드·키가 필요하고, 지금은 도메인/클라우드 세팅 전이다.

**결정** 우선 **로컬 볼륨 저장**으로 간다(사용자 선택). `FileStorageService` 가 업로드 파일을
`app.upload-dir`(배포는 docker 볼륨 `/app/uploads`) 에 UUID 파일명으로 저장하고 공개 경로
`/uploads/<파일>` 를 돌려준다. 원본 파일명은 안 쓴다(경로조작·충돌 차단). 콘텐츠 타입 image/*
+ 확장자 화이트리스트 + 5MB 제한으로 이중 검증. `WebMvcConfig` 리소스 핸들러가 `/uploads/**`
를 저장 디렉터리로 서빙하고, SecurityConfig 는 GET `/uploads/**` 를 permitAll. PMS 객실 폼은
URL 입력칸을 없애고 **파일 업로드 3칸**(미리보기·삭제 체크)으로 바꿨다. 컨트롤러가 슬롯별로
새 파일이면 저장 후 옛 파일 삭제·교체, 삭제 체크면 비움, 없으면 기존 유지.

저장·삭제를 `FileStorageService` 한 곳에 모아, 정식 배포 때 **오브젝트 스토리지(R2)로 옮길 땐
이 클래스 내부만 교체**하면 되게 했다(호출부 불변). 데모 시드는 이미지를 비워 둬 큐레이션
폴백(D-052)이 뜨고, 운영자가 업로드하면 그 이미지로 대체된다.

**검증** 전체 백엔드 스위트 그린. 관리자 로그인→객실 수정 폼에 실제 jpg 멀티파트 업로드→302,
API `imageUrls` 에 `/uploads/…` 반영, `GET /uploads/<파일>` 200(image/jpeg·123KB), 부킹엔진
RoomsPage 가 그 이미지를 표시(1장이라 캐러셀 컨트롤 없음)함을 dev/8080 실측. 검증 후 원복.

## D-054. 예약 1뎁스·세 구간 반응형·국내 연락처·카카오맵

**맥락** 메인 예약 폼이 가용 수량을 보여준 뒤 다시 “이 객실 예약”을 눌러야 해 전환 단계가
불필요하게 길었고, 부킹엔진 상단 메뉴와 PMS 고정 사이드바는 태블릿·모바일에서 조작하기
어려웠다. 국내 데모 단계에서 연락처 형식과 위치 안내도 일관된 기준이 필요했다.

**결정** 메인 폼은 조건을 `/book`으로 바로 넘기고 그 화면에서 가용·요금·객실 요약을 조회한다.
재고 HOLD는 최종 제출 때만 만든다. 로그인 회원의 예약자 정보는 서버가 회원 프로필에서 다시
읽고, 비회원만 직접 입력한다. 화면 폭은 모바일(≤767)·태블릿(768~1199)·데스크톱(≥1200)의
세 구간으로 통일하며 부킹엔진은 드로어 내비, PMS는 아이콘 레일/오프캔버스를 쓴다. 연락처는
이번 단계에서 국내 010 휴대전화와 이메일을 프론트·서버 양쪽에서 검증하고 공통 모듈로 분리해
추후 국가 선택+E.164로 확장한다. 위치는 결제 계정이 필요한 Google Maps 동시 지원 대신 국내
사용 경험이 나은 카카오맵 고정 좌표를 쓰고, 키가 없거나 로드 실패 시 이미지·외부 링크로 폴백한다.

**검증** 프론트 프로덕션 빌드·lint, 전체 백엔드 테스트, 390/768/1024/1440px 대표 폭에서
가로 넘침·내비 동작·메인→예약 1클릭 이동을 확인한다. Docker 8080 재빌드 후 기존 DB·업로드
볼륨과 객실 이미지가 유지되는지 회귀 확인한다.
