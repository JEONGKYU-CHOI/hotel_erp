## D-001. 프론트엔드 — 하이브리드 (부킹엔진 React / 백오피스 Thymeleaf)

**결정일** 2026-07-29

**결정**

| 영역 | 기술 | 인증 |
|---|---|---|
| 부킹엔진 (고객) `/` | React + Vite | 없음 (비회원 예약) |
| 백오피스 `/admin/**` | Thymeleaf + Bootstrap | 세션 쿠키 (Spring Security) |
| API `/api/**` | REST (부킹엔진 전용) | 없음 |

**이유**

1. **포지션이 진짜 풀스택(반반)** — 프론트 코드도 면접 검토 대상이므로 React 산출물이 필요하다.
2. **프론트 역량 증명에 화면 개수는 기여하지 않는다** — 잘 만든 5화면 > 대충 만든 15화면.
   부킹엔진은 보여줄 것이 있다(날짜 범위 선택, 잔여 재고 표시, 결제 플로우, 예약 상태 전이).
   백오피스 CRUD 15개를 React로 만드는 것은 같은 폼의 반복 노동이며 역량 증명에 기여하지 않는다.
3. **JWT 인증 비용(약 8h)을 회피한다** — 고객용 부킹엔진은 비회원 예약(예약번호+전화번호 조회)이라
   인증이 아예 없다. 백오피스는 Thymeleaf라 Spring Security 세션 쿠키 기본값으로 끝난다.
   전면 React였다면 관리자 인증을 위해 JWT 발급/저장/갱신을 직접 설계해야 했다.
4. **CORS가 발생하지 않는다** — 개발 중에는 Vite 프록시, 배포 시에는 React 빌드 결과물을
   스프링 `static/`에 포함해 단일 오리진. 배포 산출물은 JAR 하나로 유지된다.
5. **실무에서 흔한 패턴** — 고객 대면 SPA + 어드민 서버 렌더링. 근거를 설명할 수 있으면
   "일관성 없음"이 아니라 의사결정이다.

**감수하는 대가**

- 스택이 둘이라 프로젝트 구조가 복잡해진다 (`frontend/` 디렉토리 + Gradle-npm 빌드 연동).
- React 라우팅을 위한 SPA fallback 설정이 필요하다 (`/admin/**`, `/api/**`와 경로 충돌 주의).
- 백오피스 프론트 코드는 포트폴리오의 프론트 역량 증거로 쓸 수 없다.

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| 전부 Thymeleaf | 포지션이 풀스택 반반이므로 프론트 산출물이 없으면 절반을 포기하는 셈 |
| 전부 React | 백오피스 15화면 React화에 약 15h. 반복 노동이며 역량 증명 기여도 낮음. 관리자 JWT 인증 비용 추가 |

**기각된 근거 (기록용)**

"등록 → 예약 → 결제를 직접 해보고 싶다"는 목적은 React 선택 근거가 **아니다**.
해당 흐름은 Thymeleaf로 동일하게 구현되며, 특히 결제는 토스페이먼츠 SDK가 어차피 JS이고
핵심(금액 위변조 검증, 멱등성, 승인 API 호출, 재고 복원, 웹훅 중복 처리)은 전부 서버 코드다.
React 선택의 유효한 근거는 **풀스택 포지션에서 프론트가 평가 대상이라는 점** 하나다.

## D-002. ORM — JPA 단독 (락·통계는 native query)

**결정일** 2026-07-29

**결정** Spring Data JPA 단독 사용. MyBatis를 추가하지 않는다.
재고 락 쿼리와 통계 쿼리는 `@Query(nativeQuery = true)`로 SQL을 직접 작성한다.

**이유**

1. MyBatis는 이미 실무 경험이 있어 포트폴리오에서 재증명할 가치가 낮다. 새로 배우는 JPA가 가치다.
2. **혼용하면 도망갈 길이 생긴다** — 재고 락에서 JPA가 막히는 순간 "이건 MyBatis로 짜자"가 되고,
   그러면 JPA 도입 목적이 소멸하며 "왜 둘 다 썼나"에 답할 서사도 없다.
3. 락 쿼리는 native query로 쓰면 `ORDER BY stay_date FOR UPDATE`가 코드에 명시적으로 드러나
   오히려 설명하기 좋다.
4. 서사가 명확해진다 — "MyBatis 실무자가 JPA로 전환하며, 락이 필요한 지점만 SQL을 되찾아온 이유".

**감수하는 대가**

- JPA 학습 곡선을 정면으로 맞는다 (실무 경험 없음). Day 0 스파이크로 완화한다.
- 통계 쿼리를 JPQL로 쓰기 어려워 native query 비중이 늘어난다.

**폐기한 대안** JPA + MyBatis 혼용 — 위 2번 사유.

## D-003. 임시점유(Hold) — DB 상태 + 스케줄러 (Redis 미사용)

**결정일** 2026-07-29

**결정** 별도 Hold 테이블을 두지 않는다. 예약 자체를 `status = HOLD`로 생성하고
`hold_expires_at` 컬럼으로 만료를 관리한다. 스케줄러가 만료분을 `EXPIRED`로 전환하며
`room_inventory.held_qty`를 차감한다.

**이유**

1. **Redis는 재고 진실의 출처를 둘로 만든다** — Redis와 DB가 어긋나면 곧 오버부킹이다.
   동시성 정합성이 주제인 프로젝트에서 정합성 위험을 자진 도입할 이유가 없다.
2. Redis TTL을 써도 **DB 재고 복원은 별도 코드가 필요하다** — 만료 이벤트를 받아 DB를 고쳐야 하므로
   인프라만 늘고 문제는 그대로다.
3. 예약을 HOLD 상태로 만들면 **예약번호를 미리 발급해 PG에 넘길 수 있고**, 결제 성공 시
   상태만 전이하면 된다 (행 이동 불필요).
4. 만료된 HOLD가 `EXPIRED`로 남아 이탈 예약 통계가 부수적으로 확보된다.
5. 면접 가치 — "Redis 썼습니다"보다 "Redis를 검토하고 안 쓴 이유"가 강하다.

**감수하는 대가**

- 스케줄러 주기만큼 재고 반환이 지연된다.
  → **완화**: 가용 재고 조회 시 `hold_expires_at < NOW()` 인 건을 만료로 취급하면
    사용자에게는 지연이 보이지 않는다. 스케줄러는 정리(cleanup)만 담당한다.
- `reservation` 테이블에 EXPIRED 행이 누적된다 (감사 가치가 있어 삭제하지 않음).

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| Redis TTL | 재고 진실의 출처 이원화. DB 복원 코드는 어차피 필요 |
| 별도 `hold` 테이블 | `reservation.status = HOLD`로 충분. 테이블만 늘어남 |

## D-004. 야간마감 배치 — `@Scheduled` + 직접 구현 (Spring Batch 미사용)

**결정일** 2026-07-29

**결정** Spring Batch를 쓰지 않고 `@Scheduled` + 마감 이력 테이블 + 유니크 제약으로
멱등성을 직접 구현한다.

**이유**

1. **Spring Batch를 쓰면 재실행 방지를 프레임워크가 해준다** — 그러면 "제가 설계했습니다"라고
   말할 수 없다. 이 프로젝트의 핵심 기술 과제 ③이 멱등성 설계인데 그것을 위임하면 가치가 사라진다.
2. 러닝커브가 크고(Job/Step/Reader/Writer/Chunk), 메타 테이블 6개가 DB에 생긴다.
3. 마감은 하루 1회 실행이라 청크 처리·재시작 같은 Batch의 강점이 필요 없다.

**감수하는 대가**

- 재시도·스킵·재시작 같은 배치 인프라를 직접 만들어야 한다 (범위를 좁혀 대응).
- "왜 Spring Batch를 안 썼나" 질문에 답변을 준비해야 한다.

**폐기한 대안** Spring Batch — 위 1번 사유.

## D-005. 스키마 관리 — Flyway + `ddl-auto: validate`

**결정일** 2026-07-29

**결정** Flyway로 마이그레이션 SQL을 직접 작성하고, Hibernate는 `ddl-auto: validate`로
검증만 시킨다. `update`를 쓰지 않는다.

**이유**

1. **핵심 설계가 Hibernate 자동생성으로는 나오지 않는다** —
   데드락 방지의 핵심인 `INDEX (room_type_id, stay_date)`와
   최후 방어선인 `CHECK (sold_qty + held_qty <= total_qty)`는 SQL로 직접 써야 한다.
2. **JPA 무경험 상태에서는 `validate`가 안전장치다** — 엔티티 매핑이 틀렸을 때
   테이블을 조용히 바꿔버리는 대신 애플리케이션 시동이 실패한다.
3. 스키마 변경 이력이 파일로 남아 "스키마 변경을 어떻게 관리했나"에 답할 수 있다.

**감수하는 대가** 엔티티를 고칠 때마다 마이그레이션 SQL을 함께 써야 한다 (의도된 마찰).

**폐기한 대안** `ddl-auto: update` — 위 1·2번 사유.

## D-006. 테스트 — 핵심 3과제 통합테스트 + Testcontainers

**결정일** 2026-07-29

**결정** 전 도메인 테스트를 포기하고 핵심 3과제에 통합테스트를 집중한다.
DB는 H2가 아닌 **Testcontainers로 실제 MySQL**을 띄운다.

필수 테스트 3종:
1. 동시 예약 시 오버부킹 0건 (JUnit + `CountDownLatch`)
2. Hold 만료 시 재고 복원
3. 야간마감 2회 실행 시 중복 게시 없음

**이유**

1. **H2로는 `FOR UPDATE`의 행 락이 재현되지 않는다** — 갭 락·넥스트키 락 동작이 다르고
   데드락도 발생하지 않는다. "오버부킹 0건"이 이 프로젝트의 핵심 주장인데
   그 증명을 다른 DB에서 하면 주장 자체가 무너진다.
2. JMeter보다 JUnit 동시성 테스트를 우선한다 —
   세팅 30분 vs 2~3h, **테스트 코드가 리포에 남고** 면접관이 직접 돌려볼 수 있다.
   JMeter는 시간이 남으면 처리량 수치용으로 추가한다.

**감수하는 대가** 테스트 실행 시 Docker가 떠 있어야 하고 실행 시간이 길어진다.

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| H2 인메모리 DB | 행 락 재현 불가 → 동시성 테스트가 무의미 |
| JMeter 우선 | 세팅 비용이 크고 결과물이 리포에 남지 않음 |

## D-007. 백로그로 이관한 항목

**결정일** 2026-07-29

| 항목 | 이관 사유 |
|---|---|
| 멀티테넌시 | 진짜 비용은 컬럼이 아니라 **모든 쿼리에 필터를 강제하는 것**(Hibernate `@Filter`/인터셉터). 하나라도 누락되면 테넌트 간 데이터 유출. JPA 무경험 상태에서 다루기 위험. → **`tenant_id` 컬럼만 미리 두고 전부 `1` 고정** |
| AI 모듈 (Gemini) | 백엔드 트랙으로 확정. 추후 추가한다면 자연어 재고 조회(text-to-SQL, 검증 어렵고 프롬프트 인젝션 위험)보다 **예약 이상 탐지**(룰 기반 폴백 가능 → 실패 경로 설계 증명)가 낫다 |
| 회원가입/로그인 | 비회원 예약(예약번호+전화번호)이 실제 호텔 직판 사이트의 방식. JWT 인증 비용 회피 |
| 채널매니저 / OTA 연동 | 1차 범위 밖 |
| Spring Batch | D-004 참조 |
