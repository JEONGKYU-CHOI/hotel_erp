## D-001. 프론트엔드 — 하이브리드 (부킹엔진 React / 백오피스 Thymeleaf)

**결정일** 2026-07-29
**부분 폐기** 인증 부분은 [D-008](#d-008-부킹엔진-인증--jwt-d-001-부분-supersede)이 대체한다.
아래 표의 "인증 = 없음" 항목은 더 이상 유효하지 않다. 프론트 기술 선택은 그대로 유효하다.

**결정**

| 영역 | 기술 | 인증 |
|---|---|---|
| 부킹엔진 (고객) `/` | React + Vite | ~~없음 (비회원 예약)~~ → **JWT (D-008)** |
| 백오피스 `/admin/**` | Thymeleaf + Bootstrap | 세션 쿠키 (Spring Security) |
| API `/api/**` | REST (부킹엔진 전용) | ~~없음~~ → **JWT (D-008)** |

**이유**

1. **포지션이 진짜 풀스택(반반)** — 프론트 코드도 면접 검토 대상이므로 React 산출물이 필요하다.
2. **프론트 역량 증명에 화면 개수는 기여하지 않는다** — 잘 만든 5화면 > 대충 만든 15화면.
   부킹엔진은 보여줄 것이 있다(날짜 범위 선택, 잔여 재고 표시, 결제 플로우, 예약 상태 전이).
   백오피스 CRUD 15개를 React로 만드는 것은 같은 폼의 반복 노동이며 역량 증명에 기여하지 않는다.
3. **JWT 인증 비용(약 8h)을 회피한다** — 고객용 부킹엔진은 비회원 예약(예약번호+전화번호 조회)이라
   인증이 아예 없다. 백오피스는 Thymeleaf라 Spring Security 세션 쿠키 기본값으로 끝난다.
   전면 React였다면 관리자 인증을 위해 JWT 발급/저장/갱신을 직접 설계해야 했다.
4. **CORS가 발생하지 않는다** — 개발 중에는 Vite 프록시, 배포 시에는 React 빌드 결과물을
   스프링 `static/`에 포함해 단일 오리진. 배포 산출물은 JAR 하나로 유지된다.
5. **실무에서 흔한 패턴** — 고객 대면 SPA + 어드민 서버 렌더링. 근거를 설명할 수 있으면
   "일관성 없음"이 아니라 의사결정이다.

**감수하는 대가**

- 스택이 둘이라 프로젝트 구조가 복잡해진다 (`frontend/` 디렉토리 + Gradle-npm 빌드 연동).
- React 라우팅을 위한 SPA fallback 설정이 필요하다 (`/admin/**`, `/api/**`와 경로 충돌 주의).
- 백오피스 프론트 코드는 포트폴리오의 프론트 역량 증거로 쓸 수 없다.

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| 전부 Thymeleaf | 포지션이 풀스택 반반이므로 프론트 산출물이 없으면 절반을 포기하는 셈 |
| 전부 React | 백오피스 15화면 React화에 약 15h. 반복 노동이며 역량 증명 기여도 낮음. 관리자 JWT 인증 비용 추가 |

**기각된 근거 (기록용)**

"등록 → 예약 → 결제를 직접 해보고 싶다"는 목적은 React 선택 근거가 **아니다**.
해당 흐름은 Thymeleaf로 동일하게 구현되며, 특히 결제는 토스페이먼츠 SDK가 어차피 JS이고
핵심(금액 위변조 검증, 멱등성, 승인 API 호출, 재고 복원, 웹훅 중복 처리)은 전부 서버 코드다.
React 선택의 유효한 근거는 **풀스택 포지션에서 프론트가 평가 대상이라는 점** 하나다.

## D-002. ORM — JPA 단독 (락·통계는 native query)

**결정일** 2026-07-29

**결정** Spring Data JPA 단독 사용. MyBatis를 추가하지 않는다.
재고 락 쿼리와 통계 쿼리는 `@Query(nativeQuery = true)`로 SQL을 직접 작성한다.

**이유**

1. MyBatis는 이미 실무 경험이 있어 포트폴리오에서 재증명할 가치가 낮다. 새로 배우는 JPA가 가치다.
2. **혼용하면 도망갈 길이 생긴다** — 재고 락에서 JPA가 막히는 순간 "이건 MyBatis로 짜자"가 되고,
   그러면 JPA 도입 목적이 소멸하며 "왜 둘 다 썼나"에 답할 서사도 없다.
3. 락 쿼리는 native query로 쓰면 `ORDER BY stay_date FOR UPDATE`가 코드에 명시적으로 드러나
   오히려 설명하기 좋다.
4. 서사가 명확해진다 — "MyBatis 실무자가 JPA로 전환하며, 락이 필요한 지점만 SQL을 되찾아온 이유".

**감수하는 대가**

- JPA 학습 곡선을 정면으로 맞는다 (실무 경험 없음). Day 0 스파이크로 완화한다.
- 통계 쿼리를 JPQL로 쓰기 어려워 native query 비중이 늘어난다.

**폐기한 대안** JPA + MyBatis 혼용 — 위 2번 사유.

## D-003. 임시점유(Hold) — DB 상태 + 스케줄러 (Redis 미사용)

**결정일** 2026-07-29

**결정** 별도 Hold 테이블을 두지 않는다. 예약 자체를 `status = HOLD`로 생성하고
`hold_expires_at` 컬럼으로 만료를 관리한다. 스케줄러가 만료분을 `EXPIRED`로 전환하며
`room_inventory.held_qty`를 차감한다.

**이유**

1. **Redis는 재고 진실의 출처를 둘로 만든다** — Redis와 DB가 어긋나면 곧 오버부킹이다.
   동시성 정합성이 주제인 프로젝트에서 정합성 위험을 자진 도입할 이유가 없다.
2. Redis TTL을 써도 **DB 재고 복원은 별도 코드가 필요하다** — 만료 이벤트를 받아 DB를 고쳐야 하므로
   인프라만 늘고 문제는 그대로다.
3. 예약을 HOLD 상태로 만들면 **예약번호를 미리 발급해 PG에 넘길 수 있고**, 결제 성공 시
   상태만 전이하면 된다 (행 이동 불필요).
4. 만료된 HOLD가 `EXPIRED`로 남아 이탈 예약 통계가 부수적으로 확보된다.
5. 면접 가치 — "Redis 썼습니다"보다 "Redis를 검토하고 안 쓴 이유"가 강하다.

**감수하는 대가**

- 스케줄러 주기만큼 재고 반환이 지연된다.
  → **완화**: 가용 재고 조회 시 `hold_expires_at < NOW()` 인 건을 만료로 취급하면
    사용자에게는 지연이 보이지 않는다. 스케줄러는 정리(cleanup)만 담당한다.
- `reservation` 테이블에 EXPIRED 행이 누적된다 (감사 가치가 있어 삭제하지 않음).

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| Redis TTL | 재고 진실의 출처 이원화. DB 복원 코드는 어차피 필요 |
| 별도 `hold` 테이블 | `reservation.status = HOLD`로 충분. 테이블만 늘어남 |

## D-004. 야간마감 배치 — `@Scheduled` + 직접 구현 (Spring Batch 미사용)

**결정일** 2026-07-29

**결정** Spring Batch를 쓰지 않고 `@Scheduled` + 마감 이력 테이블 + 유니크 제약으로
멱등성을 직접 구현한다.

**이유**

1. **Spring Batch를 쓰면 재실행 방지를 프레임워크가 해준다** — 그러면 "제가 설계했습니다"라고
   말할 수 없다. 이 프로젝트의 핵심 기술 과제 ③이 멱등성 설계인데 그것을 위임하면 가치가 사라진다.
2. 러닝커브가 크고(Job/Step/Reader/Writer/Chunk), 메타 테이블 6개가 DB에 생긴다.
3. 마감은 하루 1회 실행이라 청크 처리·재시작 같은 Batch의 강점이 필요 없다.

**감수하는 대가**

- 재시도·스킵·재시작 같은 배치 인프라를 직접 만들어야 한다 (범위를 좁혀 대응).
- "왜 Spring Batch를 안 썼나" 질문에 답변을 준비해야 한다.

**폐기한 대안** Spring Batch — 위 1번 사유.

## D-005. 스키마 관리 — Flyway + `ddl-auto: validate`

**결정일** 2026-07-29

**결정** Flyway로 마이그레이션 SQL을 직접 작성하고, Hibernate는 `ddl-auto: validate`로
검증만 시킨다. `update`를 쓰지 않는다.

**이유**

1. **핵심 설계가 Hibernate 자동생성으로는 나오지 않는다** —
   데드락 방지의 핵심인 `INDEX (room_type_id, stay_date)`와
   최후 방어선인 `CHECK (sold_qty + held_qty <= total_qty)`는 SQL로 직접 써야 한다.
2. **JPA 무경험 상태에서는 `validate`가 안전장치다** — 엔티티 매핑이 틀렸을 때
   테이블을 조용히 바꿔버리는 대신 애플리케이션 시동이 실패한다.
3. 스키마 변경 이력이 파일로 남아 "스키마 변경을 어떻게 관리했나"에 답할 수 있다.

**감수하는 대가** 엔티티를 고칠 때마다 마이그레이션 SQL을 함께 써야 한다 (의도된 마찰).

**폐기한 대안** `ddl-auto: update` — 위 1·2번 사유.

## D-006. 테스트 — 핵심 3과제 통합테스트 + Testcontainers

**결정일** 2026-07-29

**결정** 전 도메인 테스트를 포기하고 핵심 3과제에 통합테스트를 집중한다.
DB는 H2가 아닌 **Testcontainers로 실제 MySQL**을 띄운다.

필수 테스트 3종:
1. 동시 예약 시 오버부킹 0건 (JUnit + `CountDownLatch`)
2. Hold 만료 시 재고 복원
3. 야간마감 2회 실행 시 중복 게시 없음

**이유**

1. **H2로는 `FOR UPDATE`의 행 락이 재현되지 않는다** — 갭 락·넥스트키 락 동작이 다르고
   데드락도 발생하지 않는다. "오버부킹 0건"이 이 프로젝트의 핵심 주장인데
   그 증명을 다른 DB에서 하면 주장 자체가 무너진다.
2. JMeter보다 JUnit 동시성 테스트를 우선한다 —
   세팅 30분 vs 2~3h, **테스트 코드가 리포에 남고** 면접관이 직접 돌려볼 수 있다.
   JMeter는 시간이 남으면 처리량 수치용으로 추가한다.

**감수하는 대가** 테스트 실행 시 Docker가 떠 있어야 하고 실행 시간이 길어진다.

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| H2 인메모리 DB | 행 락 재현 불가 → 동시성 테스트가 무의미 |
| JMeter 우선 | 세팅 비용이 크고 결과물이 리포에 남지 않음 |

## D-008. 부킹엔진 인증 — JWT (D-001 부분 supersede)

**결정일** 2026-07-29

**결정** 부킹엔진(`/` React)과 `/api/**`의 인증을 **JWT**로 한다.
D-001의 "부킹엔진 인증 없음"을 대체한다. 백오피스 세션 쿠키 방식은 그대로 둔다.

**이유**

1. **D-009로 회원가입/로그인이 1차 범위에 들어왔다.** 로그인이 있으면 인증 수단이 필요하다.
2. **SPA + REST에 세션 쿠키를 쓰면 설명이 길어진다** — CSRF 토큰 처리, 쿠키 SameSite 설정이
   따라붙는다. 부킹엔진은 이미 별도 오리진 없이 단일 JAR로 나가지만(D-001),
   REST API의 상태 없음(stateless)을 유지하는 편이 서사가 깔끔하다.
3. **인증 방식이 두 개인 것 자체가 설명 가치가 된다** — "왜 같은 앱에서 백오피스는 세션,
   고객은 JWT인가"는 면접에서 답할 수 있는 질문이다.
   (세션은 서버가 상태를 들고 즉시 무효화할 수 있어 직원 계정에 적합하고,
   JWT는 상태가 없어 고객 트래픽에 유리하되 즉시 무효화가 어렵다.)
4. **비회원 예약 경로는 그대로 남는다.** JWT는 로그인 사용자에게만 추가되는 선택지이고,
   예약번호+전화번호 조회는 인증 없이 계속 동작한다.

**감수하는 대가**

- D-001에서 회피하려던 인증 비용(약 8h)을 다시 진다.
- 토큰 저장 위치(메모리 vs localStorage) 선택과 XSS 노출 논점이 생긴다.
- Spring Security 설정이 두 갈래(세션 체인 + JWT 필터 체인)로 나뉜다.

**폐기한 대안** 부킹엔진 세션 쿠키 — 위 2번 사유.

## D-009. 회원가입/로그인을 1차 범위로 편입 (D-007 부분 supersede)

**결정일** 2026-07-29

**결정** D-007에서 백로그로 뺐던 회원가입/로그인을 1차 범위로 되돌린다.
`member` 테이블은 V1 스키마에 이미 들어가 있다.

**이유**

1. **비회원 예약만 있으면 React 쪽에 보여줄 것이 얇다** — D-001이 React를 택한 근거는
   "프론트가 평가 대상"인데, 로그인·토큰 갱신·인증 상태에 따른 라우팅 분기는
   프론트 역량이 실제로 드러나는 지점이다.
2. **BCrypt 해싱·인증 필터는 백엔드에서도 흔히 묻는 주제다.** 없으면 포트폴리오에 구멍이 된다.
3. 비용 재평가 — D-007 시점에는 "전면 React + 관리자 JWT"를 가정해 8h로 봤다.
   실제로는 고객 로그인 하나이고 권한 체계도 단순해 비용이 그보다 작다.

**감수하는 대가** 1차 범위가 늘어난다. 대신 D-010으로 범위를 좁혀 상쇄한다.

## D-010. JWT는 Access Token 단독 — 리프레시 로테이션은 백로그

**결정일** 2026-07-29

**결정** Access Token 하나만 발급한다(만료 시 재로그인).
Refresh Token 발급·저장·로테이션·재사용 탐지는 구현하지 않는다.

**이유**

1. **리프레시 로테이션을 제대로 하려면 서버 저장소와 재사용 탐지가 필요하다** —
   토큰 저장 테이블, 회전 시 이전 토큰 무효화, 탈취 탐지 시 계정 전체 무효화까지
   가야 의미가 있다. 어중간하게 만들면 "리프레시 토큰을 그냥 오래 살려둔 것"이 되고
   보안상 더 나쁘다.
2. **이 프로젝트의 핵심 주제는 동시성·정합성이지 인증이 아니다.** 인증에 시간을 더 쓰면
   핵심 3과제(오버부킹 0건, Hold 만료 복원, 마감 멱등성)가 얇아진다.
3. 재로그인 UX 저하는 데모 범위에서 문제되지 않는다.

**감수하는 대가**

- 토큰 만료 시 사용자가 다시 로그인해야 한다.
- "리프레시 토큰은 왜 없나" 질문에 답할 준비가 필요하다 (위 1번이 답).

**폐기한 대안** Access + Refresh 로테이션 — 위 1·2번 사유. 백로그로 이관.

## D-011. Spring Boot 4.0.7 (4.1.0 아님)

## D-014. `member` / `staff_user` 테이블 분리

**결정일** 2026-07-29

**결정** 고객 회원과 직원 계정을 한 테이블에 role로 구분하지 않고 **테이블을 나눈다.**

**이유**

1. **인증 경로가 애초에 다르다** — 고객은 JWT(D-008), 직원은 세션 쿠키(D-001).

**감수하는 대가**

- 인증 설정이 두 벌 필요하다 (D-008에서 이미 감수하기로 한 비용과 같다).
- 두 테이블에 공통 컬럼(password_hash 등)이 중복된다.

**폐기한 대안** 단일 `user` 테이블 + role 컬럼 — 위 2번 사유가 결정적.

## D-016. SQL 로깅 — Hibernate 내장 (p6spy 미사용)

**결정일** 2026-07-29

**결정** `org.hibernate.SQL: DEBUG` + `org.hibernate.orm.jdbc.bind: TRACE`로 SQL과
바인딩 파라미터를 본다. p6spy(또는 datasource-proxy)를 추가하지 않는다.

**감수하는 대가** 로그가 SQL과 파라미터 두 줄로 나뉘어 p6spy처럼 한 줄 완성 SQL로 보이지 않는다.
락 검증에는 지장이 없다.

**폐기한 대안** p6spy — 위 2번 사유.

## D-018. 재고를 읽는 **첫 조회**가 락 조회여야 한다

**결정일** 2026-07-29 (Day 0 비관적 락 스파이크의 결과)

**결정** 예약 트랜잭션에서 `room_inventory`를 읽을 때, **맨 처음 읽는 쿼리부터**
`FOR UPDATE`여야 한다. "먼저 가용 재고를 조회해 보여주고, 확정 단계에서 락을 잡는다"는
순서를 같은 트랜잭션 안에서 쓰지 않는다.

**이유 — 실측으로 확인했다.** 락을 나중에 거는 코드는 **락을 잡고도 옛 값을 읽는다.**
원인이 두 겹이라 한쪽만 알면 못 막는다.

1. **영속성 컨텍스트(1차 캐시)가 DB 결과를 버린다.** 이미 영속 상태인 인스턴스가 있으면
   JPA는 `SELECT ... FOR UPDATE`를 실제로 보내고 락도 잡지만, DB가 돌려준 최신 행을
   버리고 캐시에 있던 인스턴스를 반환한다. 스파이크에서 `locked.get(0) == inventory`가
   `true`로 찍혔다.
2. **락 없는 읽기는 REPEATABLE READ 스냅샷을 본다.** MySQL 기본 격리수준에서 일반 SELECT는
   트랜잭션이 처음 읽은 시점의 스냅샷을 읽는다. 그래서 `EntityManager.refresh()`로도
   최신 값이 오지 않는다.
3. **`refresh(entity, PESSIMISTIC_WRITE)`로도 회복되지 않았다.** 기대와 달리
   `for update`가 붙지 않은 평범한 `select ... where id=?`가 나갔다(실측).

결과: DB의 실제 `sold_qty`가 2인 동안 트랜잭션 안에서는 네 번의 조회가 모두 1을 반환했다.
이 상태로 재고를 검사하면 **락을 걸었는데도 오버부킹이 난다.** 이 프로젝트의 핵심 주장이
정면으로 무너지는 지점이다.

**어떻게 지킬 것인가**

- 재고 조회 경로를 둘로 분리한다.
  가용 재고 **표시용**(락 없음, 읽기 전용 트랜잭션) / 예약 **확정용**(첫 쿼리부터 `FOR UPDATE`).
- 확정 트랜잭션 안에서는 표시용 조회 메서드를 호출하지 않는다.
- 검증은 Day 2 동시성 통합테스트(D-006)가 맡는다. 오버부킹 0건이 이 규칙의 회귀 테스트다.

**감수하는 대가** 예약 확정 경로에서 재고를 미리 훑어보는 최적화를 쓸 수 없다.
락 범위가 트랜잭션 전체로 넓어져 경합이 커진다 — 그래서 확정 트랜잭션을 짧게 유지해야 한다.

**근거** 스파이크 코드와 실행 로그: `io.github.jeongkyuchoi.hotel.erp.common.support.spike.PessimisticLockSpike`.
실행 방법과 실측 결과는 그 클래스 주석과 커밋 `7a08a53` 메시지에 있다.

## D-019. 엔티티 매핑 공통 규약

**결정일** 2026-07-30

**결정** 모든 엔티티에 다음을 강제한다.

| 항목 | 규칙 | 예외 |
|---|---|---|
| `@ManyToOne` | **항상 `fetch = LAZY`** | 없음 |
| 상태값 | `@Enumerated(EnumType.STRING)` | 없음 |
| 금액 | `BigDecimal` + `precision`/`scale` 명시 | 없음 |
| DB `TINYINT` | 자바 `int` + `@JdbcTypeCode(SqlTypes.TINYINT)` | 없음 |
| 연관관계 | 탐색이 필요하면 `@ManyToOne`, 기록이면 `Long` | `RoomInventory.roomTypeId`(락 경로), `ReservationNight.roomTypeId`(스냅샷 기록) |

**이유**

1. **`@ManyToOne` 의 기본값이 EAGER 다.** 명시하지 않으면 목록 조회 한 번에 연관 테이블
   조회가 건마다 따라붙는다(N+1). 기본값이 위험한 쪽이므로 규약으로 못 박는다.
   대가는 목록 쿼리마다 `join fetch` 를 직접 써야 하는 것이다 —
   `RoomRepository.findAllForList` 가 그 예다.
2. **`EnumType.ORDINAL` 은 enum 상수 순서를 바꾸는 순간 기존 데이터의 의미가 통째로 달라진다.**
   `CANCELLED` 를 목록 중간에 끼워 넣는 흔한 변경이 과거 예약 상태를 전부 밀어버린다.
   스키마도 `VARCHAR + CHECK` 로 잡혀 있어 STRING 과 그대로 맞물린다.
3. **`double` 은 부동소수 오차로 정산이 어긋난다.** 숙박일수만큼 더하는 구조라
   오차가 누적된다.
4. **`TINYINT` ↔ `int` 는 `ddl-auto: validate` 가 기동을 실패시킨다.** 실제로 겪었다.
   자바 타입을 `byte` 로 바꾸는 대안은 인원 계산마다 int 로 승격돼 캐스팅만 늘어난다.

**감수하는 대가**

- 목록 조회마다 `join fetch` 쿼리를 직접 써야 한다(LAZY 의 대가).
- 상태값을 문자열로 저장해 `ORDINAL`(정수)보다 저장 공간을 더 쓴다. 무시할 수준이다.

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| `@ManyToOne` 기본값(EAGER) 사용 | 조용한 N+1. 문제를 발견하기 어렵다 |
| `EnumType.ORDINAL` | 위 2번. 데이터 손상이 조용히 일어난다 |
| 전부 `Long` FK (연관관계 없음) | 백오피스 화면에서 타입 이름을 찍는 것조차 서비스에서 조립해야 한다 |

## D-020. 기준정보는 삭제하지 않고 비활성화한다

**결정일** 2026-07-30

**결정** 객실타입·호실·요금정책에 물리 삭제(DELETE) 기능을 만들지 않는다.
`active` 플래그를 끄는 것으로 대신한다. 목록 화면의 버튼도 "삭제"가 아니라
"판매중단 / 사용중지"다.

**이유**

1. **애초에 지울 수 없다.** 호실·요금정책·재고·예약이 FK 로 참조하고 있어
   DELETE 가 제약 위반으로 실패한다. 되는 것처럼 화면을 만들면 사용자가
   누를 때마다 알아볼 수 없는 예외를 본다.
2. **지울 수 있게 만들면 과거 예약이 무의미해진다.** "2026년 8월에 어떤 객실타입을
   얼마에 팔았는가"를 답할 수 없게 된다. 정산·감사에서 필요한 정보다.
3. **판매 중단은 삭제가 아니다.** 실무에서 필요한 것은 "더 이상 팔지 않는다"이지
   "존재한 적 없다"가 아니다. 비활성화가 요구를 정확히 표현한다.

**감수하는 대가**

- 잘못 만든 데이터가 목록에 계속 남는다. 화면이 지저분해진다.
  → 완화: 정렬에서 뒤로 밀거나 필터를 추가한다(현재는 미구현).
- 코드(`code`)를 재사용할 수 없다. 유니크 제약이 비활성 행에도 걸려 있기 때문이다.

**폐기한 대안**

| 대안 | 폐기 이유 |
|---|---|
| 물리 삭제 | 위 1·2번 |
| soft delete 컬럼(`deleted_at`) 추가 | `active` 와 의미가 겹친다. 상태가 둘이면 "비활성인데 삭제 안 됨"이 무슨 뜻인지 답해야 한다 |

## D-021. 운영 상태값은 기준정보 화면에서 편집하지 않는다

**결정일** 2026-07-30

**결정** 업무 흐름이 바꾸는 상태값은 기준정보 폼에서 제외한다.
첫 적용 대상은 `room.occupancy_status`(공실/투숙중)다. 수정 화면에 **표시는 하되
`disabled`** 로 두고, 폼 DTO(`RoomForm`)에 아예 필드를 두지 않는다.

반대로 `room.clean_status`(청결)는 편집을 허용한다.

**이유**

1. **점유 상태는 예약과 체크인/체크아웃이 소유한 값이다.** 기준정보 화면에서 임의로
   `VACANT` 로 되돌릴 수 있으면, 투숙 중인 방에 다른 손님을 배정하는 사고가 난다.
   화면에서 막는 것으로 부족해 **폼 DTO 에 필드를 두지 않는다** — 요청 파라미터를
   직접 만들어 보내도 바인딩될 대상이 없다.
2. **청결 상태는 다르다.** 고장으로 인한 `OUT_OF_ORDER` 처리는 기준정보 담당의 일이고,
   업무 흐름이 자동으로 판단해 주지 않는다.
3. **이 구분이 상태를 2축으로 나눈 설계의 값을 실현한다.** 한 컬럼이었다면
   "고장이면서 투숙중"을 표현할 수 없고, 편집 가능/불가를 나눌 수도 없다.

**적용 범위** 앞으로 만들 화면에도 같은 기준을 적용한다.
`reservation.status`, `reservation_night.posted`, `room_inventory.sold_qty`/`held_qty`
는 전부 업무 흐름이 소유한다. 관리자가 직접 고쳐야 하는 상황이 생기면
그것은 폼이 아니라 **사유를 남기는 별도 기능**으로 만든다.

**감수하는 대가**

- 데이터가 꼬였을 때 화면으로 손볼 수 없어 DB 를 직접 만져야 한다.
  → 그것이 맞다. 손으로 고칠 수 있으면 왜 꼬였는지 아무도 조사하지 않는다.

**폐기한 대안** 전 항목 편집 허용 — 위 1번 사유.

## D-022. 요금 캘린더 생성은 락을 걸지 않는다 (재고 생성과 대비)

**결정일** 2026-07-30

**결정** `rate_calendar` 행을 만들 때, 기존 행을 **락 없는 일반 조회**로 읽어 병합한다.
재고 생성(`InventoryService.generate`)이 첫 조회부터 `lockForUpdateNative`(D-018)로
시작하는 것과 반대다. 구조는 둘 다 "날짜 범위에 행 펼치기"로 같지만 락 정책이 다르다.

**이유**

1. **요금표는 예약 트랜잭션이 동시에 잠그는 행이 아니다.** 예약은 `room_inventory`의
   `sold_qty`/`held_qty`를 올릴 뿐, `rate_calendar`를 건드리지 않는다. 그래서
   "락을 걸었는데 옛 값을 읽는다"(D-018)는 문제가 성립할 경합 상대가 없다.
2. **예약 금액은 확정 순간 `reservation_night`에 스냅샷으로 복사된다.** 요금표를
   나중에 바꿔도 과거 예약 금액이 흔들리지 않는다. 즉 요금표 수정과 예약은 시간적으로
   분리돼 있다.
3. **요금표를 바꾸는 주체는 관리자 한 명(ADMIN 전용 경로)이다.** 관리자 두 명이
   같은 날짜를 동시에 저장하는 드문 경합은 유니크 제약 `uk_rate_calendar`가 막는다.
   비관적 락까지 갈 필요가 없다.

이 대비가 "왜 저기(재고)는 락을 걸고 여기(요금)는 안 거는가"에 대한 답이다.
락은 습관이 아니라 **동시에 같은 행을 놓고 다투는 경합이 있을 때만** 건다.

**감수하는 대가**

- 관리자 두 명이 같은 요금정책·같은 날짜를 밀리초 차이로 동시에 저장하면 나중 것이
  이긴다(last-write-wins). 요금 설정 업무 특성상 문제되지 않는다.

**폐기한 대안** 재고와 동일하게 `FOR UPDATE` — 경합 상대가 없어 락 비용만 늘어난다.

**검증** admin 로그인 후 2026-08-03(월)~08-09(일) 범위에 주중 100,000 / 주말 150,000으로
생성해 주말 2일만 15만원이 적용됨을 확인했다(요일별 차등). 같은 값으로 재생성 시
`생성 0 · 갱신 0 · 유지 7`로 멱등하게 동작하고, STAFF 계정은 이 경로에서 403을 받는다.

## D-023. 예약 HOLD 생성 서비스 설계

**결정일** 2026-07-30

**결정** 예약을 `status=HOLD` 로 만드는 서비스(`ReservationService.hold`)를 다음 규칙으로 짠다.

1. **재고 락 우선(D-018 첫 적용).** 이 트랜잭션에서 재고를 처음 읽는 쿼리가
   `lockForUpdateNative`(FOR UPDATE)다. 표시용 조회(`findRange` 계열)는 부르지 않는다.
2. **연박은 all-or-nothing.** 어느 하루라도 재고가 부족하면 예외로 트랜잭션 전체를
   롤백해 이미 올린 다른 날짜의 `held_qty` 도 되돌린다. 부분 예약은 만들지 않는다.
3. **HOLD TTL = 10분.** 이 안에 결제하지 않으면 스케줄러가 EXPIRED 로 돌리고 재고를
   반환한다(D-003). 조회 시점에는 만료분을 만료로 취급해 지연을 감춘다.
4. **멱등키 선조회.** 유니크 제약이 최후에 막지만, 같은 키의 예약을 먼저 조회해 그대로
   돌려주는 편이 더블클릭·재시도에 대한 사용자 경험이 낫다.
5. **예약번호 = `R`+`yyMMdd`+무작위 4자리.** AUTO_INCREMENT id 를 노출하지 않는다 —
   연속 정수는 열거 공격 표면이다. 혼동 문자(0/O,1/I) 뺀 31자 집합. 충돌은 유니크
   제약+재시도로 막는다.
6. **오버부킹 3중 방어.** 도메인 `RoomInventory.hold`(가용 검사) → DB
   `CHECK(sold+held<=total)` → 이 전체를 감싸는 행 락(D-018). 어느 하나가 뚫려도
   다음이 막는다.

**이유** 화면보다 서비스를 먼저 만들어야 동시성 검증을 화면 너머가 아닌 서비스에서
직접 할 수 있다. HOLD 상태가 임시점유를 겸하므로(D-003) 별도 점유 테이블 없이
`held_qty` 증가만으로 점유가 표현된다.

**감수하는 대가**
- HOLD TTL 10분은 임의값이다. 결제 UX 실측 후 조정할 수 있다.
- 확정 트랜잭션이 재고를 잠근 채 요금표까지 조회하므로 락 보유 시간이 늘어난다.
  요금표 조회는 락 없는 다른 테이블이라 짧고, 확정 로직 자체를 짧게 유지해 상쇄한다.

**검증** Day 2 동시성 통합테스트(D-006, Testcontainers)가 오버부킹 0건으로 이 설계의
회귀 테스트를 겸한다. 단위 흐름은 그 전에 curl/부팅으로 확인한다.

**미구현(후속)** 결제 성공 시 HOLD→CONFIRMED 전이(`confirmHold`), 예약 조회/취소.
도메인 메서드는 `RoomInventory` 에 미리 넣어 두었다.
(HOLD 만료 스케줄러는 D-024 로 구현됨.)

## D-024. HOLD 만료 스케줄러 — 건별 트랜잭션 + 락 후 반환

**결정일** 2026-07-30

**결정** 만료된 HOLD 정리(D-003)를 다음 구조로 구현한다.

1. **건별 독립 트랜잭션.** 스케줄러(`HoldExpiryScheduler`)는 만료 대상 **id 목록만** 뽑아
   루프를 돌고, 예약 한 건의 만료(`ReservationExpiryService.expireOne`)는 각각 별도
   트랜잭션이다. 한 건 실패가 배치를 무너뜨리지 않고, 재고 락 보유 시간도 짧다.
   Spring `@Transactional` 자기호출 문제 때문에 루프(스케줄러)와 건별 처리(서비스)를
   **다른 빈**으로 나눈다.
2. **반환도 재고 락 우선(D-018 재적용).** `releaseHold` 는 `held_qty` 를 내리므로
   새 예약의 `hold`(증가)와 같은 행을 두고 다툰다. 되돌릴 행을 `FOR UPDATE` 로 먼저
   잠근다. 락 없이 하면 갱신 유실로 재고가 어긋난다.
3. **멱등.** `expireOne` 은 로드 후 `isHoldExpired(now)` 로 재확인해, 이미 확정·취소·
   만료됐거나 아직 만료 전이면 아무 것도 하지 않는다. 스케줄러가 겹쳐 돌거나 결제
   확정과 경합해도 재고가 이중 반환되지 않는다.
4. **시각을 파라미터로.** `sweep(now)` 가 시각을 받는다. 스케줄러는 `now()` 를 넘기고
   테스트는 미래 시각을 넘겨, 백데이트 없이 결정적으로 만료를 검증한다.

**감수하는 대가** 스케줄러 주기(1분)만큼 재고 반환이 지연된다. → 가용 재고 조회 시
만료분을 만료로 취급해(D-003) 사용자에게는 지연이 보이지 않는다. 스케줄러는 청소만 한다.

**검증** Day 2 통합테스트(D-006 ②): 2박 HOLD 를 미래 시각으로 청소 →
EXPIRED 전이 + 두 야간 `held_qty` 반환, 재실행 시 0건 처리(멱등), 만료 전 HOLD 는
무변경. 실제 MySQL 에서 통과. 동시성 테스트(D-006 ①)와 함께 회귀 테스트가 된다.

## D-025. 상태 전이는 예약 행 락으로 직렬화 (확정/만료 경합)

**결정일** 2026-07-30

**결정** HOLD 예약의 상태 전이(확정·만료, 이후 취소도)는 **예약 행을 `FOR UPDATE`로
먼저 잠근 뒤** 진행한다(`ReservationRepository.findByIdForUpdate`). 락 순서는 언제나
**예약 → 재고**로 통일한다.

**이유** 결제 확정과 HOLD 만료가 같은 예약을 거의 동시에 건드릴 수 있다(사용자가 만료
직전에 결제). 재고 락(D-018)만으로는 부족하다 — 재고에 여유가 있으면 확정과 만료가 같은
예약 행의 상태를 각자 덮어써(lost update) "EXPIRED 인데 재고는 sold" 같은 불일치가 난다.
예약 행 자체를 직렬화 지점으로 삼으면, 먼저 잠근 트랜잭션이 전이를 끝내고, 뒤이은
트랜잭션은 락 읽기로 **최신** 상태를 보고 자신의 가드로 넘어간다.
- 확정이 이기면: 만료의 `findByIdForUpdate` 가 CONFIRMED 를 읽어 `isHoldExpired=false` →
  무동작(멱등).
- 만료가 이기면: 확정이 EXPIRED 를 읽고, 재고 `confirmHold` 가 held=0 에 걸려 거부 →
  결제는 상위에서 환불로 처리.

**락 순서를 예약 → 재고로 고정하는 이유** 확정·만료 모두 이 순서를 지키면 서로 간
데드락이 없다. 예약 생성(`hold`)은 예약 행이 아직 없어 재고만 잠그므로 이 순서와 충돌하지
않는다.

**감수하는 대가** 전이마다 락이 하나 더 붙어(예약 행) 경합 시 대기가 생긴다. 전이 로직이
짧아 보유 시간은 밀리초 수준이다.

**검증** Day 2 통합테스트(D-025): 재고 1개 HOLD 에 확정과 만료를 동시 실행하는 경합을
8회 반복 → 매번 정확히 하나만 성공(CONFIRMED xor EXPIRED), held=0 유지, 승자에 따라
sold∈{0,1}. 확정 멱등(재확정 시 재고 이중 이동 없음)도 확인. 실제 MySQL 통과.
